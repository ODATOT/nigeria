# Day 1. Codex Client 기반 요구사항 정의 교육 교안 요약서

본 요약서는 일반적인 이론 교육을 넘어, 실제 기획 및 개발 워크플로우를 그대로 따르는 **프로젝트 기반 학습(PBL)**과 **Codex Client**를 접목한 실습 가이드입니다. 

---

## 📌 Part 1. 왜 Codex Client를 사용하는가?

### 1. ChatGPT와 Codex Client의 결정적 차이

일반적인 ChatGPT 웹 대화창과 다중 파일 프로젝트 단위의 Codex Client는 요구사항 설계 시 접근 방식부터 다릅니다.

| 비교 항목 | 일반 ChatGPT (웹 브라우저) | Codex Client (Workspace 기반) |
|---|---|---|
| **작업 인지 범위** | 현재 입력창에 입력한 단발성 텍스트만 인식 | 프로젝트 폴더(Workspace) 내의 모든 파일 인식 |
| **파일 제어 방식** | 화면에 출력된 결과 코드를 수동 복사·붙여넣기 | AI가 지정된 마크다운 파일을 직접 생성 및 부분 수정 |
| **다중 파일 추론** | 이전 파일의 연계 수정을 위해 매번 수동 업로드 필요 | 하나의 기획 변경 시 연계된 다른 파일 내용 동시 추론 |

### 2. Workspace(프로젝트) 개념
* **로컬 폴더 = 프로젝트 = Workspace**입니다.
* 명세에 필요한 여러 마크다운 파일들(`meeting-notes.md`, `functional-requirements.md` 등)이 하나의 폴더에 존재할 때, 이 폴더를 통째로 AI에 연결하여 **콘텍스트(Context) 저장소**로 사용하는 단위를 뜻합니다.

## 📌 Part 2. 실습 목표

### 1. 오늘 만들 최종 결과물
* **통합 요구사항 정의서 (`requirements-specification.md`)**: 회의록 원본에서 시작하여 검증 및 승인이 완료된 정형 명세서.
* **Gmail 플러그인 전송 메일**: Gmail API 플러그인을 사용하여 이해관계자(대표 등)에게 모호한 예외 사항에 대해 최종 의사결정을 요청하는 실제 이메일 발송 완료.

### 2. Input / Output 시퀀스 연결성

```text
[📥 Input: 대화록 원본] ──► (Codex Client) ──► [💾 Output: 핵심 요약 메모]
                                                    │
                                                    ▼
[📥 Input: 요약 메모]   ──► (Codex Client) ──► [💾 Output: 객체 분류 & 요구사항 정의서]
                                                    │
                                                    ▼
[📥 Input: 요구사항 표]   ──► (Codex Client) ──► [💾 Output: 시나리오 상세화 & 기획 질문지]
                                                    │
                                                    ▼
[📥 Input: 명세 파일들]  ──► (Codex Client + Gmail Plugin) ──► [💾 Output: 통합 사양서 & Gmail 발송 완료]
```

### 3. 단계별 상세 데이터 파이프라인 규격

#### 🔧 준비 단계. 로컬 작업 폴더 및 AI 연동 세팅
* **작업 공간 (Input)**: 학습자 컴퓨터 바탕화면의 빈 폴더 `automation/`
* **연동 결과 (Output)**: Codex Client 내에 `automation/` 프로젝트 연동 완료
* **요약 설명**: 사용자가 로컬에 전용 디렉토리를 구축하고, Codex AI 환경에 해당 경로를 열어 문서들을 쓰고 읽는 채널을 확보합니다.
* **수행 프롬프트**: 로컬 바탕화면에 `automation` 폴더를 생성하고 Codex Client를 실행합니다.

#### 0단계. 상세 대화록에서 핵심 요약 도출 (전처리)
* **단계 입력 (Input)**: `meeting-notes-raw.md` (회의 시 오고 간 사담이 섞인 핑퐁 대화록)
* **단계 출력 (Output)**: `meeting-notes.md` (불필요한 문맥을 걷어낸 15줄 핵심 요약 메모)
* **요약 설명**: 분석 노이즈를 줄이기 위해, 비정형 회의록에서 핵심 요구사항 요건을 뽑아 압축된 기획 요약으로 전처리합니다.
* **수행 프롬프트**: `meeting-notes-raw.md의 회의록 원문을 읽고, 화자 간의 불필요한 대화 맥락과 문맥을 걷어내고 서비스 사용자, 기능 요건, 시스템 정책, 미결정 유보 사항을 15줄 내외의 컴팩트한 비정형 요약 메모 형태로 작성해줘. 원문에 없는 가상의 내용은 임의로 상상해서 추가하지 말아줘.`

#### 1단계. 요약된 기획 메모 요건 분석
* **단계 입력 (Input)**: `meeting-notes.md`
* **단계 출력 (Output)**: 분류된 기획 객체 목록 (사용자 역할, 기능 후보, 비즈니스 정책, 미결정 사항)
* **요약 설명**: 비정형 텍스트 요약 메모를 바탕으로 기획 요소를 4가지(사용자, 기능, 정책, 미결정) 성격에 따라 분리/구조화합니다.
* **수행 프롬프트**: `meeting-notes.md를 읽고 다음 내용을 구분해줘. 1. 서비스 사용자 2. 사용자가 수행하는 기능 3. 시스템이 수행하는 기능 4. 비즈니스 규칙 5. 아직 결정되지 않은 사항. 회의 메모에 없는 내용은 추가하지 말고 불명확한 내용은 별도로 표시해줘.`

#### 2단계. 기능 요구사항 문장 정의 (FR 테이블)
* **단계 입력 (Input)**: 분류된 기획 객체 목록 (1단계 출력)
* **단계 출력 (Output)**: `functional-requirements.md` (테스트 가능한 명세 표 구조 요구사항 명세서)
* **요약 설명**: 객체로 쪼개진 기능들을 `[사용자/시스템]은 [특정 조건]에서 [동작]해야 한다`는 엄격한 테스팅 규칙에 맞게 기능 명세 문장으로 작성합니다.
* **수행 프롬프트**: `1단계에서 추출한 기능 후보를 기능 요구사항으로 작성해줘. 요구사항 ID는 FR-001부터 순서대로 부여하고, 하나의 요구사항에는 하나의 기능만, 사용자를 명확히 적고, 모호한 표현을 제외하고 Markdown 표로 출력해줘.`

#### 3단계. 시나리오 보완 (정상 및 예외 흐름)
* **단계 입력 (Input)**: `functional-requirements.md` 초안 표
* **단계 출력 (Output)**: 정상/예외 흐름 및 검증 기준이 포함된 상세 `functional-requirements.md`
* **요약 설명**: 주 기능의 정상 흐름 외에, 시스템 장애/데이터 중복/결제 실패 등 발생 가능한 비정상 예외 처리 프로세스 명세를 보충합니다.
* **수행 프롬프트**: `functional-requirements.md의 각 요구사항에 정상 흐름과 예외 흐름을 추가해줘. 정상 흐름은 시작부터 완료까지 단계별로 작성하고, 예외 흐름은 실패, 중복, 데이터 없음 상황을 검토하며 임의 결정하지 않고 확인 필요로 명시해줘.`

#### 4단계. 미결정 기획 질문지 추출
* **단계 입력 (Input)**: 기획 명세 내 '추가 확인 필요' 항목
* **단계 출력 (Output)**: `open-questions.md` (질문 ID, 우선순위, 영향 범위 등이 정리된 공식 의사결정 요청서)
* **요약 설명**: 개발 착수 전, 이해관계자의 조율이 반드시 선행되어야 하는 쟁점들을 식별하고 명문화해 기획 수정 피드백 루프를 가동합니다.
* **수행 프롬프트**: `현재 요구사항 문서를 검토해서 확정되지 않았거나 모호한 내용을 찾아줘. 각 항목을 기획자가 이해관계자에게 확인할 수 있는 질문 형태로 작성하고, 관련 ID, 결정 필요 이유, 영향 기능, 우선순위 표로 만들어줘.`

#### 5단계. 문서 통합 및 Gmail 발송 (플러그인)
* **단계 입력 (Input)**: `meeting-notes.md`, `functional-requirements.md`, `open-questions.md` 및 Gmail 플러그인 연동
* **단계 출력 (Output)**: `requirements-specification.md` 및 이메일 발송 완료
* **요약 설명**: 산발적인 마크다운 명세들을 하나의 승인 명세 파일로 병합하고, Gmail 플러그인을 사용하여 의사결정권자에게 기획 승인 보고 메일을 자동으로 대행 전송합니다.
* **수행 프롬프트**: `Gmail 플러그인을 사용하여 방금 검증 완료된 requirements-specification.md 내용과 open-questions.md의 미결정 사항들을 요약해 [의사결정권자 메일 주소]로 기획 승인 요청 메일을 전송해줘.`

## 📌 Part 3. 따라하기 (Codex Client 실제 UI 가이드)

학습자는 Codex Client 실제 UI 화면에서 바탕화면에 빈 폴더를 준비한 뒤, **샘플 회의록 파일을 생성하는 기초 동작부터 시작**하여 실습을 완수합니다.

### STEP 1. 프로젝트 폴더 생성 및 선택
* **행동**: 바탕화면에 빈 폴더인 **`automation`** 폴더를 생성하고, Codex Client 좌측의 **`프로젝트`** 목록 창에서 `automation` 폴더를 클릭하여 연결합니다.
* **상태**: 현재 폴더 안은 아무 파일도 존재하지 않는 깨끗한 빈 상태입니다.

### STEP 2. 실습용 샘플 파일 생성 지시 (최초 생성)
* **행동**: 하단 프롬프트 입력창을 클릭하고 아래의 지시문을 붙여넣은 뒤 우측 **[빌드]** 버튼을 누릅니다.
  > "프로젝트 폴더 내에 meeting-notes-raw.md 파일을 생성하고 아래의 1차 Kick-off 회의록 대화 내용을 작성해줘. [내용: 대표(CEO)가 온라인 전문가 상담 서비스를 만들려 한다고 회의를 제안하고, 기획자(PM)가 회원가입에 대해 질문하며, 결제 완료 시 예약이 확정되고 취소 정책은 보류하기로 결정했다는 대화 내용]"
* **결과**: 좌측 탐색기 내부에 `meeting-notes-raw.md` 파일이 최초로 생성되고 저장됩니다.

### STEP 3. Prompt 입력 (요약 전처리 요청)
* **행동**: 원본 파일이 준비되었으므로, 프롬프트 입력창에 요약 가공 지시문을 작성합니다.
  > "meeting-notes-raw.md를 읽고 핵심 기획 요안 요약본인 meeting-notes.md를 생성해줘."

### STEP 4. Codex 실행 (요약 파일 빌드)
* **행동**: 입력창 우측의 [빌드] 버튼을 클릭합니다.
* **AI 동작**: AI가 폴더 내의 `meeting-notes-raw.md`를 알아서 찾아 읽은 후, 기획 분석에 알맞게 정제된 핵심 요약 파일 `meeting-notes.md`를 생성하여 프로젝트 폴더 내에 저장합니다.

### STEP 5. Gmail 플러그인 설치 및 메일 전송
* **행동**:
  1. Codex Client 우측 상단 플러그인 스토어에서 **`Gmail` 플러그인을 설치**하고 구글 계정을 OAuth 연동합니다.
  2. 프롬프트 창에 아래 명령을 날려 통합 요구사항과 기획 질문지를 요약한 메일을 실제로 발송합니다.
     > "Gmail 플러그인을 사용하여 방금 검증 완료된 requirements-specification.md 내용과 open-questions.md의 미결정 사항들을 요약해 [의사결정권자 메일]로 기획 승인 요청 메일을 즉시 전송해줘."
* **확인**: 본인 메일의 '보낸 메일함'에서 실제 이메일 발송 여부를 최종 확인합니다.

## 📌 Part 4. 왜 이렇게 되었는가? (작동 원리 및 의의)

### 1. Codex Client의 파일 탐색 및 플러그인 연동 메커니즘
* Codex Client는 사용자가 프로젝트 폴더를 여는 순간부터 디렉토리의 파일 구조를 캐싱하고 감시합니다. 또한, 연동된 Gmail 플러그인 API를 직접 호출해 메일을 작성하고 대행 발송하는 등 외부 서비스와 긴밀히 융합 작동합니다.

### 2. 왜 파일들이 유기적으로 연결되고 생성되는가?
* 1단계(`meeting-notes.md`)를 분석해 작성된 2단계(`functional-requirements.md`) 및 4단계(`open-questions.md`)는 동일한 서비스 객체를 바라보고 있습니다. 
* 파일 이름들이 명확하고 서로 내용이 연계되어 있을 때, Codex Client는 이들 간의 의존관계를 파악하여 데이터 충돌 없이 문서를 병합하고 린팅 경고(모호성 검출)를 제공할 수 있는 것입니다.

### 3. 다음 단계 설계로의 확장성
* 오늘 구축한 명세 파일들은 단순 문서로 끝나지 않습니다. 다음 과정에서 이 마크다운 명세들을 Codex Client에 인풋으로 넣어주면, AI가 **DB 설계서(ERD), 백엔드 API 명세, 프론트엔드 와이어프레임 화면 설계 코드**를 자동으로 추출해내는 강력한 소스 데이터가 됩니다.

## 📌 Part 5. 미션 (PBL 과제)

### 미션 개요: 새로운 비즈니스 정책 추가 및 Gmail 플러그인 전송 자동화
* **과제**: 대표가 회의 중 추가 요건을 이야기한 상황을 연출합니다.
  1. `meeting-notes-raw.md` 문서 하단에 아래의 가상 추가 회의 내용을 수동으로 덧붙입니다.
     > **대표**: "아, 참. 회원 탈퇴 기능도 필요합니다. 탈퇴 시에는 예약된 상담이 전부 자동 취소되고 환불 처리되어야 합니다."
  2. Codex Client에게 전처리 및 분석을 재지시하여 `functional-requirements.md`에 `FR-005 회원탈퇴` 요구사항 및 예외 흐름(탈퇴 시 예약 자동 취소)이 추가되도록 명령합니다.
  3. 앞서 설정한 **Gmail 플러그인** 발송 기능을 실행하여, 최종 업데이트된 탈퇴 정책 내용과 기획 오픈 질문지를 요약한 승인 요청 메일을 대표 이메일로 즉시 자동 전송하도록 프롬프트를 보낸 후 실제로 전송 완료되었는지 메일함을 검토합니다.
