# Task 01. 불일치 검출 (Consistency Check) 실습 가이드

본 실습에서는 여러 문서 간의 정보 불일치(Consistency Issue)를 Codex Client를 활용하여 빠르게 식별하고 요약 보고서를 도출하는 방법을 배웁니다.

---

## 1. 스토리 및 실습 배경

스타트업 프로젝트 진행 중 기획자는 회의를 통해 서비스 예약 취소 위약금 정책과 회원 탈퇴 프로세스를 확정하고 회의록에 기록했습니다. 그러나 개발자는 이전 버전의 요구사항 정의서(결제 취소 미반영)를 보고 개발을 마쳤고, 디자이너는 또 다른 형태의 흐름을 반영한 화면 정의서를 기준으로 컴포넌트 디자인을 완료했습니다.

결국 출시 직전 **"회의록 정책과 실제 기능 구현 및 디자인 구성이 삼각으로 엇갈리는"** 치명적인 커뮤니케이션 불일치 장애가 발생했습니다.

기존에는 이러한 불일치 문제를 찾아내기 위해 사람이 문서를 한 자 한 자 대조해가며 검토해야 했기 때문에 많은 시간과 휴먼 에러가 수반되었습니다. 이번 실습에서는 Codex를 **"기획 검토자(Reviewer)"**로 가동하여 다중 문서 간의 모순을 자동 검출하고 조치 리포트를 구성하는 실무 요령을 익힙니다.

---

## 2. 학습 목표

* 여러 명세 문서 간의 논리적 모순과 차이점(불일치)을 비교 분석할 수 있다.
* 요구사항 정의서와 화면 정의서의 불일치 항목을 식별할 수 있다.
* 회의 합의 사항이 기획서 및 화면 설계서에 온전히 반영되었는지 검증할 수 있다.
* AI를 '정답 작성자'가 아닌 '정밀 검토자(Reviewer)'로 활용하는 실무 워크플로우를 이해한다.

---

## 3. 실습용 원본 파일 제공

실습을 위해 아래의 3개 파일 내용을 프로젝트 폴더(`automation/`)에 각각 생성해 주세요. 각 문서에는 의도적인 불일치(모순) 정책들이 숨겨져 있습니다.

### ① 회의록 (`meeting-notes.md`)
```markdown
# 온라인 전문가 상담 서비스 2차 기획 조율 회의록

* **회의 취지**: 예약 취소 정책 및 회원 탈퇴 프로세스 최종 확정
* **결정 사항**:
  1. 사용자가 예약 상담을 취소할 경우, 취소 위약금 수수료 10%를 차감한 후 환불한다.
  2. 사용자가 회원 탈퇴를 신청하면, 예약되어 있는 기존 상담 일정은 즉시 '자동 취소' 처리되고 보호 수수료 없이 '전액 환불'한다.
  3. 서비스 투명성을 위해 일반 사용자(Customer)가 상담이 끝난 후 전문가(Expert)를 평가할 수 있는 '별점 리뷰 및 평가 기능'을 제공한다.
  4. 비회원은 전문가 목록과 프로필 조회만 가능하며, 예약 신청 버튼은 비활성화 상태여야 한다.
```

### ② 요구사항 정의서 (`requirements.md`)
```markdown
# 전문가 상담 서비스 기능 요구사항 정의서

| 요구사항 ID | 사용자 | 기능명 | 요구사항 설명 |
|---|---|---|---|
| FR-001 | Customer | 회원가입 | 사용자는 이메일 인증을 통해 회원가입을 완료할 수 있다. |
| FR-002 | Customer | 전문가 검색 | 사용자는 분야별로 전문가를 검색할 수 있다. |
| FR-003 | Customer | 회원 탈퇴 | 사용자가 회원 탈퇴 시, 기존 예약 상담 정보는 시스템 안전을 위해 '보관(유지)' 상태로 유지된다. |
| FR-004 | Expert | 별점 평가 | 전문가는 상담이 종료된 후 상담을 받은 사용자(Customer)를 평가할 수 있는 별점 기능을 가진다. |

*주의: 본 요구사항 정의서에는 예약 결제 취소(환불) 기능 관련 요구사항이 정의되어 있지 않음.*
```

### ③ 화면 정의서 (`screen-specification.md`)
```markdown
# 전문가 상담 서비스 화면 설계 및 흐름 정의서

1. **비회원 홈 화면 (SCR-001)**:
   - 비회원 상태에서 전문가 목록을 볼 수 있다.
   - 각 전문가 카드 하단에 '상세보기' 및 '예약하기' 버튼이 모두 활성화되어 노출된다. (클릭 시 가입 유도 없이 바로 예약 일정 선택 화면으로 이동)

2. **회원 탈퇴 화면 (SCR-002)**:
   - 사용자가 '탈퇴하기' 버튼을 누르면 즉시 탈퇴가 처리되며 로그인 화면으로 튕긴다. (별도의 예약 취소 프로세스나 안내 팝업창은 노출되지 않으며, 예약 데이터는 화면 상에서만 숨김 처리됨)

3. **상담 종료 화면 (SCR-003)**:
   - 상담이 종료되면 화면 우측에 '상담사 평가' 팝업이 출력되며, 일반 사용자(Customer)가 전문가(Expert)에게 별점(1~5점)을 부여할 수 있다.
```

## 4. Codex 수행 및 프롬프트 가이드

학습자는 Codex Client 하단 프롬프트 입력창에 아래 지시문을 복사하여 보낸 뒤 **[빌드]** 버튼을 누릅니다.

### Codex 요청 프롬프트 (검토 지시)
```text
프로젝트 폴더 내에 있는 'meeting-notes.md', 'requirements.md', 'screen-specification.md' 세 문서를 비교 분석해줘.

각 문서 간에 서로 모순되거나 불일치하는 항목, 혹은 한쪽 문서에만 존재하고 다른 문서에서는 누락된 항목을 찾아서 정리해줘.
결과는 아래 요구사항에 맞춰 출력해줘.

1. 결과는 '구분(기능/화면/정책/용어 등)', '발견 내용 및 모순점', '영향도(높음/중간/낮음)', '권한이 가장 높은 기준 문서', '권장 조치' 칼럼을 가진 Markdown 표 형태로 정리해줘.
2. 개발 및 테스트 진입 시 치명적인 리워크(재작업)를 유발할 수 있는 사항은 영향도를 '높음'으로 표기해줘.
3. 임의의 해답을 창조하지 말고 문서 텍스트에 기반해서 팩트 위주로만 비교 분석 결과를 도출해줘.
```

## 5. 결과물 예시

Codex는 프롬프트를 해석하여 아래와 같이 일목요연한 불일치 요약 리포트를 표 형태로 생성합니다.

| 구분 | 발견 내용 및 모순점 | 영향도 | 기준 문서 | 권장 조치 |
|---|---|---|---|---|
| **정책/기능** | 회의록에는 예약 취소 시 10% 수수료 환불 정책이 확정되었으나, 요구사항 정의서(`requirements.md`)에는 관련 내용이 완전히 누락됨. | **높음** | 회의록 | 요구사항 정의서에 예약 취소 및 10% 위약금 환불 기능 요구사항 추가 반영 필요 |
| **정책/화면** | 회원 탈퇴 시 기존 예약에 대해 회의록은 '자동 취소 및 전액 환불'이라 정의했으나, 요구사항서에는 '보관 유지', 화면정의서에는 '안내 팝업 없이 숨김 처리'로 세 문서가 모두 상이함. | **높음** | 회의록 | 기획팀 조율을 거쳐 회의록 기준으로 요구사항과 화면 정의서의 탈퇴 로직 일체화 수정 필요 |
| **기능/화면** | 회의록 및 화면정의서에서는 '사용자(Customer)가 전문가(Expert)를 평가'하도록 설계되었으나, 요구사항서(FR-004)에는 '전문가(Expert)가 사용자(Customer)를 평가'하도록 주체가 반대로 작성됨. | **높음** | 회의록 | 요구사항 정의서의 FR-004 평가 주체를 Customer로 수정 반영 |
| **화면** | 회의록에는 비회원의 경우 '예약 신청 버튼 비활성화'를 명시했으나, 화면정의서(SCR-001)에는 '비회원 예약하기 버튼 활성화' 및 가입 유도 없는 일정 진입으로 모순됨. | **중간** | 회의록 | 화면 정의서의 비회원 홈화면 예약 흐름을 '비활성화 또는 가입 팝업 유도'로 수정 |

## 6. AI 활용 포인트

* **다중 파일 크로스 체크**: 텍스트 데이터의 맥락을 동시에 비교하여 문서 간의 의미적 오류(모순) 검출.
* **영향도 우선순위화**: 시스템 개발에 병목이 되는 결제/정책 충돌 요소를 판단하여 우선순위 분류.
* **조치 조언 획득**: 모순을 해결하기 위해 기획서가 가야 할 명확한 방향(Action Item) 도출.

---

## 7. 학습 포인트

> **⚠️ 핵심 인식의 전환**
> "AI는 정답 명세서를 뚝딱 써주는 요술 램프가 아닙니다. 사람이 여러 문서를 대조하며 밤새워 찾아야 하는 **논리적 모순과 구멍(차이)을 단 몇 초 만에 찾아내 주는 가장 꼼꼼한 검토 비서(Reviewer)**입니다."

실무 프로젝트에서 가장 비싼 비용이 들어가는 시점은 '개발이 끝난 뒤 기획 오류를 발견해 시스템을 엎을 때'입니다. Codex를 파이프라인의 검수자로 배치하면 기획자, 디자이너, 개발자가 각자 다른 버전의 명세서를 쥐고 엉뚱한 제품을 만드는 대참사를 미연에 방지할 수 있습니다.

# Task 02. 변경사항 관리 (Change Management)

## 1. 스토리 및 실습 배경

프로젝트가 진행되면서 비즈니스 전략에 맞춰 고객의 요구사항이 대대적으로 변경되었습니다. 초기 기획안(v1.0)에서는 단순 이메일 아이디 로그인만 지원하기로 했었지만, 회의 결과 사용자 가입률 향상을 위해 Google 소셜 로그인 기능이 추가되었습니다. 또한 보안 강화를 위해 회원가입 시 휴대폰 SMS 인증 절차를 거치도록 하였고, 백오피스 관리를 위해 관리자(Admin) 권한 구분을 신설하기로 최종 조율되었습니다.

하지만 이 변경된 정책이 모든 산출물에 유기적으로 반영되지 않았습니다. 그 결과 기획 요구사항 정의서만 일부 수정된 채 화면 설계서와 백엔드 API 명세서는 여전히 이전 v1.0 기준의 회원 가입/로그인 스펙을 쥐고 개발팀에 배포되었습니다.

이번 실습에서는 Codex를 활용하여 변경 전과 변경 후의 요구사항 파일을 동적으로 대조하고, 변경 내용에 영향받는 화면(Screen), API 기능(Feature), 문서를 식별해 변경 이력 및 영향 범위 맵을 자동으로 정리하는 기법을 학습합니다.

---

## 2. 학습 목표

* 변경 전과 변경 후 요구사항 정의서의 변경점을 정확히 비교 분석할 수 있다.
* 특정 기능 변경이 시스템 하위 요소(화면 UI, 연동 API 규격)에 미치는 영향 범위를 식별할 수 있다.
* 시스템 변경 이력(Change Log)을 구조적으로 작성하고 관리할 수 있다.
* AI를 활용하여 영향도 분석(Impact Analysis) 과정을 단축하여 휴먼 에러를 방지할 수 있다.

## 3. 실습용 원본 파일 제공

실습을 위해 아래의 4개 파일 내용을 프로젝트 폴더(`automation/`)에 각각 생성해 주세요.

### ① 변경 전 요구사항 (`requirements-before.md`)
```markdown
# 기능 요구사항 정의서 v1.0 (변경 전)

| 요구사항 ID | 사용자 | 기능명 | 요구사항 설명 |
|---|---|---|---|
| FR-AUTH-01 | Customer | 로그인 | 사용자는 이메일 주소와 비밀번호를 사용하여 로그인할 수 있다. |
| FR-AUTH-02 | Customer | 회원가입 | 사용자는 이메일 주소를 입력하고 이메일 인증 링크를 눌러 가입을 완료한다. |
| FR-AUTH-03 | System | 권한부여 | 가입 완료 시 시스템은 모든 사용자에게 일반 사용자(User) 권한을 자동으로 부여한다. |
```

### ② 변경 후 요구사항 (`requirements-after.md`)
```markdown
# 기능 요구사항 정의서 v2.0 (변경 후)

| 요구사항 ID | 사용자 | 기능명 | 요구사항 설명 |
|---|---|---|---|
| FR-AUTH-01 | Customer | 로그인 | 사용자는 이메일 로그인 외에 Google 소셜 계정을 연동하여 로그인할 수 있다. |
| FR-AUTH-02 | Customer | 회원가입 | 사용자는 회원 가입 신청 후 휴대폰 번호 입력을 통한 SMS 인증번호 확인 절차를 거쳐 가입을 완료한다. |
| FR-AUTH-03 | System | 권한구분 | 시스템 권한 정책은 일반 사용자(User) 권한과 시스템 관리자(Admin) 권한으로 다원화하여 부여한다. |
```

### ③ 화면 정의서 (`screen-specification-v2.md`)
```markdown
# 화면 설계서 (v1.0 기준 잔존 문서)

1. **로그인 화면 (SCR-01)**:
   - 이메일 입력 필드, 비밀번호 입력 필드, 그리고 '로그인' 버튼만 노출된다.

2. **회원가입 화면 (SCR-02)**:
   - 이메일 입력 필드, '인증메일 발송' 버튼이 제공된다. 클릭 시 이메일 링크 인증 가이드 팝업창이 출력된다.

3. **마이페이지 화면 (SCR-03)**:
   - 일반 회원용 프로필 정보 및 예약 현황 화면만 표시된다. 관리자용 모니터링 메뉴나 페이지 전환 흐름은 설계되어 있지 않다.
```

### ④ API 명세서 (`api-specification.md`)
```markdown
# 백엔드 회원인증 API 규격서 (v1.0 기준 잔존 문서)

* **로그인 API**:
  - `POST /api/v1/auth/login`
  - 요청 Payload: `{ "email": "string", "password": "string" }`

* **회원가입 API**:
  - `POST /api/v1/auth/signup`
  - 요청 Payload: `{ "email": "string", "password": "string" }`
```

# Task 03. 의사결정 추적 (Decision Tracking)

## 1. 스토리 및 실습 배경

프로젝트 회의에서는 수많은 아이디어와 열띤 논쟁이 펼쳐지며 다양한 비즈니스 정책들이 결정됩니다. 하지만 바쁜 일정에 쫓겨 단순 회의 내용이나 최종 결정 사항만 듬성듬성 기록해 두다 보면, 시간이 지난 후 **"이 결정을 왜 내렸는지"** 배경과 논리적 근거(Context)가 실종되는 경우가 허다합니다.

예를 들어, "이번 1차 배포에서는 Apple 로그인을 제외하고 Google 로그인만 적용하기로 결정했다"는 결과 정보는 회의록에 남아 있지만, "당시 회의실에서 **왜 Apple 로그인을 배제했는지(비용? 기간? 정책?)**, **누가 최종 서명했는지**, **언제 이 의사결정이 이뤄졌는지**" 이력이 남아 있지 않다면, 신규 팀원이 합류하거나 2차 개발 논의 시 똑같은 쟁점을 두고 무의미한 회의 핑퐁을 다시 거쳐야 합니다.

이번 실습에서는 Codex를 활용하여 비정형 구두 회의록, 메신저 대화록, 변경 요청 메일에서 의사결정의 주체, 날짜, 원인, 배경 근거를 정밀 추출하고 프로젝트 추적을 위한 **의사결정 이력(Decision Log)** 및 **미결 안건(Pending Items)** 체크리스트를 정밀 빌드하는 방식을 학습합니다.

## 2. 학습 목표

* 회의록 및 대화 기록에서 의사결정 사항의 배경, 날짜, 담당자를 명확히 분류할 수 있다.
* 단순 의견 개진 사항과 최종 의사결정이 승인된 완료 사항을 구별할 수 있다.
* 결론이 나지 않아 향후 재확인이 요구되는 미결 사항(Pending/Action Items)을 구조적으로 정리할 수 있다.
* AI를 활용하여 텍스트 대화 파일에서 비즈니스 결정 이력(Decision Log)을 실시간 구조화할 수 있다.

이 실습 과정들을 유기적으로 학습하면, 학생들은 실제 실무 프로젝트 관리에서 가장 난해해하는 **"무엇이 불일치하는가 ➔ 어떻게 변경하고 통제할 것인가 ➔ 왜 그런 결정을 내렸는가 ➔ 어떤 범위에 영향을 미치고 현안은 무엇인가"**라는 프로젝트 요구사항 생애주기 관리(Requirements Lifecycle Management)를 AI 검수 비서와 완수하는 최고급 기획 역량을 획득하게 됩니다.

# Mission 1 (Task 06). 영향도 분석 (Impact Analysis)

## 1. 스토리 및 실습 배경

프로젝트 진행 중 고객으로부터 다음과 같은 요구사항 변경 요청이 접수되었습니다.
> "사용자 경험 및 보안성 향상을 위해 회원가입 시 휴대폰 번호를 통한 SMS 인증 절차를 추가해 주세요."

겉으로 보기에는 간단한 텍스트 필드 하나가 늘어나는 작은 수정처럼 느껴지지만, 실제로는 회원가입 화면(UI), 로그인/회원인증 로직, User DB 테이블 구조, 백엔드 인증 API 명세서, 나아가 관리자 대시보드 화면까지 전방위적인 설계 수정과 DB 스키마 갱신이 필요합니다.

이번 실습에서는 Codex를 활용하여 단일 변경 요청이 프로젝트 하위의 다양한 설계 산출물과 문서들에 어떤 연쇄 영향을 미치는지(Ripple Effect) 분석하고, 수정이 필요한 범위와 구체적인 조치 사항을 일목요연하게 영향도 보고서로 자동 정리하는 기법을 체득합니다.

---

## 2. 학습 목표

* 변경 요청 사항(Change Request)의 전파 경로 및 영향 범위(Impact Boundary)를 분석할 수 있다.
* 변경에 의해 직접적인 수정이 요구되는 하위 요소(화면 UI, DB 스키마, API 규격)를 논리적으로 식별할 수 있다.
* 관련 명세 문서의 수정 이력과 영향도 맵을 정형 구조화할 수 있다.
* AI 비서를 활용하여 영향도 분석 보고서(Impact Analysis Report)를 단시간 내에 효율적으로 작성할 수 있다.

---

## 3. 실습 미션

학습자는 Codex Client 프롬프트 입력창에 아래 지시문을 복사하여 보낸 뒤 **[빌드]** 버튼을 누릅니다.

> "회원가입에 휴대폰 인증 기능이 추가될 경우 영향을 받는 화면, API, DB, 문서를 모두 찾아 영향도 분석 보고서를 작성해 주세요."

---

## 4. 결과물 예시

Codex는 입력된 변경 사항을 기반으로 하위 아키텍처 및 문서에 미치는 영향을 판별해 아래와 같이 구조화된 영향도 맵 보고서를 도출합니다.

| 변경 요청 | 영향 대상 | 영향도 | 조치 사항 |
|---|---|---|---|
| **휴대폰 인증 추가** | 회원가입 화면 | **높음** | 이메일 단일 가입 폼에서 휴대폰 번호 및 인증번호 입력 폼으로 화면 기획 및 UI 수정 |
| **휴대폰 인증 추가** | 로그인/가입 API | **중간** | 가입 API Payload에 phone 및 verification_code 변수 추가 및 인증 로직 수정 |
| **휴대폰 인증 추가** | User DB | **높음** | Users 테이블 내 휴대폰 번호(`phone`) 및 인증 확인 여부(`is_verified`) 컬럼 추가 |
| **휴대폰 인증 추가** | 관리자 화면 | **낮음** | 관리자 백오피스 회원 정보 조회 목록에 휴대폰 번호 표시 항목 추가 |

---

## 5. AI 활용 포인트

* **영향 범위 자동 매핑**: 비정형 변경 요구에서 DB, API, UI 등 연계 아키텍처 요소로의 종속성 추론.
* **조치 사항 상세 설계**: 변경 사항을 실무 개발자가 즉각 조치할 수 있는 수준의 구체적인 액션 아이템 지침으로 번역.
* **영향도 보고서 자동 생성**: 복잡한 아키텍처 종속 관계를 직관적인 Markdown 표 형태의 보고서로 아카이빙.

---

## 6. 학습 포인트

IT 프로젝트의 폭망 요인 1순위는 **"단순 요구사항 추가에 따른 연쇄 누락 장애"**입니다. 기획이나 개발 과정에서 "인증 폼을 추가하자"고 할 때, DB 컬럼이나 API Request 파라미터 중 어느 하나라도 누락되면 런타임 오류가 발생합니다. AI를 영향 분석 도구로 배치하면 변경 요청 한 문장으로부터 영향을 받는 모든 아티팩트 목록과 조치 가이드를 즉시 얻어 개발 안정성을 확보할 수 있습니다.

# Mission 2 (Task 07). 프로젝트 이슈 리포트 작성 (Project Issue Report)

## 1. 스토리 및 실습 배경

프로젝트 일정이 론칭 시점을 향해 치달을수록 팀원들의 회의록, 개발 진행 이력, 기획 변경 요청 사항, 아직 해결되지 않은 미결 안건(Action Items) 등이 대량으로 누적됩니다.

PM(프로젝트 매니저)은 매주 현재 프로젝트의 실질적인 진행률과 긴급하게 해결해야 할 위험 요소(Risks) 및 이슈를 취합하여 주간 상태 보고서를 작성해야 합니다. 그러나 파편화되어 널브러진 수많은 파일과 기록들을 사람이 일일이 대조하며 정리하다 보면 중요한 지연 이슈를 놓치거나 많은 수작업 리소스가 낭비됩니다.

이번 실습에서는 Codex의 Workspace 전체 맥락 인지 기능을 활용하여 프로젝트 폴더 내에 흩어진 회의록, 변경이력, Action Item, 이슈 목록 등의 파편화된 자료를 단번에 정밀 종합 분석하고, 프로젝트의 현재 상황을 긴급도 및 담당 주체별로 요약한 **프로젝트 이슈 리포트(Project Issue Report)**를 자동 빌드하는 방법을 학습합니다.

---

## 2. 학습 목표

* 다수 명세 문서와 기록에서 프로젝트 진행 상황(Status)을 논리적으로 요약할 수 있다.
* 단순 작업 내역과 실제 병목을 유발하는 긴급 이슈(Issue) 및 리스크(Risk)를 명확히 분류할 수 있다.
* 긴급도 및 영향도를 기준으로 우선 해결해야 할 과제들을 우선순위화(Prioritization)할 수 있다.
* AI를 통합 분석가로 활용하여 가독성이 뛰어난 프로젝트 주간 이슈 보고서를 자동 빌드할 수 있다.

---

## 3. 실습 미션

학습자는 아래의 가상 프로젝트 정보(회의록, 변경이력, Action Item, 이슈목록 등)가 포함된 문서를 준비한 후 Codex Client에 다음과 같이 리포트 작성을 요청합니다.

> "현재 프로젝트의 주요 이슈를 요약하고, 긴급도와 우선순위를 포함한 프로젝트 이슈 리포트를 작성해 주세요."

---

## 4. 결과물 예시

Codex는 전체 Workspace 리소스에서 작업 상태, 지연 지점, 관리 정책 미결 안건을 정확하게 파싱하여 아래와 같은 우선순위 중심의 이슈 리포트를 렌더링합니다.

| 구분 | 내용 | 우선순위 | 담당 주체 |
|---|---|---|---|
| **완료** | 로그인 및 사용자 인증 기능 구현 완료 | - | 개발팀 (Dev_Lead) |
| **진행** | 회원가입 기능(SMS 인증 연동) 개발 및 연동 진행 중 | **중간** | 개발팀 (Dev_Lead) |
| **이슈** | 외부 PG사 승인 심사 일정 지연에 따른 결제 API 연동 병목 | **높음** | PM |
| **위험** | 신규 비즈니스 요구사항 추가(해외 Paypal 결제) 예정에 따른 일정 압박 | **높음** | 기획팀 |
| **미결** | 관리자 백오피스 접근 권한 정책 및 Super/Sub 세부 인가 기준 확정 필요 | **중간** | 기획팀 |

---

## 5. AI 활용 포인트

* **다차원 데이터 통합 분석**: 회의 기록, 일정 데이터, 대화록 등 상이한 포맷의 비정형 문서 통합 분석.
* **이슈 및 리스크 자동 감지**: 단순 기록 속에서 프로젝트 위험 요소(일정 지연, 요구사항 추가 등) 식별.
* **우선순위 자동 맵핑**: 긴급도와 위험도를 기반으로 PM이 우선 처리해야 할 핵심 현안 분류.
* **주간/정기 보고서 작성 자동화**: 보고서 폼에 맞춰 구조적인 상태 보고 데이터 생성.

---

## 6. 학습 포인트

프로젝트 관리(PM)의 가장 큰 적은 **"보이지 않는 리스크"**입니다. 문서 더미 속에 묻혀 있는 "일정 지연"이나 "요구사항 추가 예정" 같은 리스크를 제때 시각화하지 못하면 골든타임을 놓치고 개발 마일스톤이 무너집니다. AI를 통합 분석 엔진으로 활용하면, 팀 내에서 생성되는 모든 작업 원본 기록을 바탕으로 즉각적인 리스크 등급 분류와 이슈 리포트를 제공받아 선제적이고 투명한 프로젝트 제어가 가능해집니다.
