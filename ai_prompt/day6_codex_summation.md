# Day 06 교육 내용 요약서 (Codex AI Workspace)

본 요약서는 Day 6 **"개발 (AI와 함께 화면 만들기)"** 교육 세션을 진행하는 강사 및 참가자들을 위한 최종 종합 요약 가이드라인입니다. 개발 초기 단계의 막연함을 극복하고 빈 화면에서 빠르게 UI 초안을 생성하는 프로토타입 설계(Task 01), 오류 메시지를 해석해 스스로 원인을 찾아 해결하는 디버깅 역량 확보(Task 02), 복잡하고 중복이 가득한 날것의 코드를 읽기 쉽고 튼튼하게 다듬는 코드 개선(Task 03) 등 AI 페어 프로그래머와 함께 실무 주도적 주니어로 성장하는 데 필요한 핵심 정보를 제공합니다.

---

## 📌 Part 1. 도입 배경 및 필요성

### 1. 개발 입문 단계의 치명적 장벽
* **빈 화면 증후군(Blank Page Syndrome)**: 기획 문서를 눈앞에 두고도 코드를 작성하는 구체적인 첫 삽을 뜨지 못해 시간만 지체되고 시작 단계에서 쉽게 포기하게 됩니다.
* **디버깅 공포 및 시간 지연**: 개발 중 발생하는 영문 에러 로그를 읽고 해석하는 단서 탐색 능력이 부족하여, 10초 만에 끝날 세미콜론 누락이나 변수명 오타를 잡느라 반나절 이상의 학습 효율을 낭비합니다.
* **유지보수가 불가능한 스파게티 코드**: 기능 동작 성공에 취해 변수명과 공통화 로직을 신경 쓰지 않은 날것의 코드를 대량 생산하면, 기능이 단 한 개만 확장되어도 시스템 전체가 연쇄 붕괴하게 됩니다.

### 2. ChatGPT vs Codex Client (Workspace 기반)
| 비교 항목 | ChatGPT (일반 대화형 AI) | Codex Client (Workspace 기반 AI) |
|---|---|---|
| **화면 초안 빌드** | 사용자가 복사해 온 부분 텍스트 기반의 단일 컴포넌트 마크업만 반환 | HTML 구조와 이를 데코레이션할 외부 CSS Flexbox/Grid 스타일 파일의 상호 연결성 및 로컬 보일러플레이트 자동 빌드 |
| **에러 원인 추적** | 에러 메시지 한 줄만 보고 피상적인 예측 코드만 제시 | 에러 스택 트레이스(Stack Trace)의 소스코드 라인 번호와 로컬 함수들 간의 비동기 호출 관계를 매핑하여 실제 원인 해결 |
| **코드 리팩토링** | 무조건 코드를 간결하게만 줄이는 식의 단조로운 축약 제안 | 협업 네이밍 컨벤션 표준, 재사용 함수 추출 매개변수 설계, 복잡도 제거 및 주석 보강을 거친 실무형 클린 리팩토링 수행 |

## 📌 Part 3. 따라하기 (Step-by-Step 실습 가이드)

### STEP 1. Task 01 - 화면 초안 빠르게 만들기
* **행동**: 대시보드 화면 명세를 담은 `day6_layout_spec.md`를 로컬 폴더에 구성하고 아래 프롬프트를 Codex에 전송합니다.
  > "제공된 레이아웃 명세를 기반으로, 예약 현황을 볼 수 있는 반응형 대시보드 화면의 HTML 마크업과 CSS 그리드 스타일 초안을 생성해 주세요. 예약 상태를 나타내는 대기/승인/완료 카드 컴포넌트와 좌측 네비게이션 바를 포함한 초기 프로젝트 구조를 제안해 주세요."
* **확인**: 생성된 HTML 파일과 CSS 파일 구조가 알맞게 생성되어, 웹브라우저에서 대시보드 3단 카드 레이아웃과 네비게이션 구도가 올바르게 잡히는지 확인합니다.

### STEP 2. Task 02 - 오류 해결 도우미
* **행동**: 런타임에 에러가 터지는 `day6_debug_source.js` 파일을 연동하여 아래 명령을 전달합니다.
  > "작성한 코드에서 'TypeError: Cannot read properties of undefined (reading 'map')' 에러가 발생했습니다. 제공된 소스코드 `day6_debug_source.js`와 콘솔 에러 로그를 대조해 에러가 발생한 원인(Why)을 초보자 눈높이에서 설명해 주고, 해당 에러를 완벽히 통제할 수 있는 방어 코드가 가미된 수정 소스를 제시해 주세요."
* **확인**: 비동기 데이터 획득 이전의 빈 값 검출 인과 관계 해설을 파악하고, 옵셔널 체이닝(`?.`)이나 조건부 조기 리턴(`if (!data)`) 방어 밸브 코드가 추가되었는지 체크합니다.

### STEP 3. Task 03 - 코드 개선하기
* **행동**: 날것의 더러운 소스 `day6_dirty_code.js`를 기준으로 리팩토링 피드백을 요구합니다.
  > "제공된 `day6_dirty_code.js` 파일의 소스를 분석하여, 1) 중복된 마크업 바인딩 로직을 공통 유틸 함수로 분리하고, 2) 모호한 변수명(ex: `a`, `temp`, `fn`)을 실무용 단어로 교정하고, 3) 향후 유지보수가 쉽도록 적절한 한 줄 주석을 작성하여 개선된 버전의 클린 코드로 리팩토링해 주세요."
* **확인**: 난해한 임시 변수들이 `formatUserPhoneNumber`처럼 읽기 쉽게 수정되었는지 확인하고, 공통 렌더링 카드 템플릿 헬퍼 함수로 중복 기능들이 정리되었는지 점검합니다.

### Mission 1. AI와 함께 오류 해결하기
* **행동**: 테스트 중 터진 CORS나 JSON 포맷 해석 실패 등의 오류 로그를 들고 디버깅을 요청합니다.
  > "서버 호출 시 발생한 'SyntaxError: Unexpected token < in JSON' 오류 메시지와 코드 파일을 기준으로, 에러 발생 배경 및 조치 코드를 반영한 최종 디버깅 보고서(Error Report)를 빌드해 주세요."
* **확인**: HTTP 응답 유형 불일치 원인을 포착하고 안전하게 예외 차단을 수행하는 디버깅 보고서 양식이 `day6_error_report.md` 파일로 잘 기재되었는지 점검합니다.

### Mission 2. AI 코드 리뷰 받기
* **행동**: 자신이 기재한 파일의 최종 렌더링 제어 코드 감사를 의뢰합니다.
  > "제공된 대시보드 상태 제어 코드를 대상으로 전역 변수 노출과 분기 코드 난립 여부를 코드 품질(Code Quality) 지표 기준으로 다각도 리뷰해 최종 개선된 리팩토링 요약서(Code Review)를 리턴해 주세요."
* **확인**: 전역 오염 캡슐화 지적과 `switch-case` 혹은 매핑 맵 구조 권유가 포함된 `day6_code_review.md` 리포트가 수치적 성장을 증명하는지 확인합니다.

## 📌 Part 4. 작동 원리 및 의의

### 1. 프로토타입 초고속 생성 (Rapid UI Prototyping)
* 기획자가 작성한 서술형 UI 사양을 컴포넌트 스타일 클래스와 그리드 템플릿으로 매핑하여 시작 코스트를 Zero에 가깝게 낮춰 주는 기법입니다.

### 2. 가독성 중심의 코드 오디팅 (Clean Code Auditing)
* 기계가 읽는 기계어로서의 작동뿐 아니라, 다른 동료 개발자(협업 주체)가 쉽게 파악할 수 있는 지적 변수명과 일관된 역할 구분을 감시하여 소프트웨어의 생존 수명을 늘리는 작업입니다.

### 3. 다섯 가지 개발 개선 마일스톤
```text
[화면 뼈대 초안 빌드] (Task 01. 시작 장벽 해소)
         │
         ▼
[오류 로그 정밀 진단] (Task 02. 디버깅 극복)
         │
         ▼
[중복 및 변수명 개선] (Task 03. 클린 리팩토링)
         │
         ▼
[예외 예방 보고서 작성] (Mission 01. 디버깅 패턴화)
         │
         ▼
[코드 다차원 정밀 감사] (Mission 02. 코드 완성 보증)
```
이 5가지 세션은 학습자가 코드 작성의 재미를 조기에 깨닫게 하고, 버그를 만났을 때 패닉에 빠지지 않으며, 스스로의 코드를 비판적(Critical)으로 다듬어 고도화하는 훌륭한 주니어의 개발 성향을 자연스럽게 주입해 줍니다.

### 💡 교육 설계 스펙
* **난이도**: ★★☆☆☆ (초급 - 완전 첫 코딩에 입문한 비전공 입문자 대상)
* **예상 실습 시간**: 1시간 30분 ~ 2시간
* **실무 활용도**: ★★★★★ (초보자의 개발 안착 속도를 비약적으로 단축)
* **학습자 질문/토의 주제**:
  1. "AI가 짜준 해결 코드가 에러를 고치는 데 성공했지만, 정작 그 코드의 세부 작동 원리를 제가 완전히 이해하지 못했다면 저는 그 코드를 실제 배포 환경에 적용해야 할까요? 이때 발생할 수 있는 잠재적 위험은 무엇인가요?"
  2. "좋은 코드란 '성능이 뛰어난 코드'와 '읽기 쉬운 코드' 중 무엇에 더 가까울까요? 비즈니스가 시시각각 바뀌는 스타트업 환경에서 이 둘의 균형을 어떻게 맞추는 것이 더 유리할까요?"
