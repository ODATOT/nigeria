The POC talk is 7 min · 4 scenes

The demo is the center. Keep slides to a minimum.

1 min · ProblemWhose pain, and what pain

Analogy · Like a Nollywood scene

A demo is one person's story, not a feature list

The audience doesn't remember buttons. They remember characters and scenes. (Example person · numbers are for explanation)

Great demo

Four principles of a good demo

Show the user's story, not a feature list.

One person's story"Ada orders lunch in under 3 minutes…"
Fewest clicksOnly the prepared path, no wandering
One failure tooShow handling of errors · sold out
One numberEvidence like time · steps · accuracy
Feedback triage

Sort feedback into three boxes

Try to fix everything and nothing gets finished.

MustBefore the final talk, for sure — core flow · trust problems
ShouldIf time allows — usability improvements
LaterAfter the MVP — new feature ideas

Make a demo script 

Based on our project's PROJECT_BRIEF.md, USER_FLOW.md and latest QA results,
make a DEMO_SCRIPT.md for a 7-minute POC talk.
- 1 min problem / 3 min live demo / 2 min how we built it (docs → AI → checks) / 1 min next steps
- The demo as one user's story (name · situation), with numbered click steps
- Include one scene showing a failure (error · sold out, etc.)
- 1–2 lines to say per scene, and a backup plan if the demo freezes
Don't add exaggerations or unchecked numbers.
