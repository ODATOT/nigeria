CHAPTER 01

Core Theory of Back-End Logic and Data Integration

Technical terms look complex, but each exists to solve one problem that keeps coming up in design. In the table below, focus on "when is it needed" more than "what does it mean."

Key conceptExplanation
TransactionGroups several data changes into one unit that succeeds or fails together.
Optimistic LockAssumes conflicts are rare and detects update conflicts by comparing versions.
Pessimistic LockLocks the resource first when conflicts are likely.
Timeout / RetryA limit on waiting for a response, and a policy for retrying temporary failures.
Circuit BreakerBriefly blocks outside calls that keep failing.
Outbox PatternA pattern that reduces mismatches between DB changes and publishing events.

The difference between good and bad design

Approach to avoid

Retry DB save, payment API and email sending endlessly inside one long request.

Recommended approach

Keep the core DB transaction short, and separate outside work with timeouts, idempotency, events and compensation policies.

Design formula

[Validate input] → [Check permission] → [Transaction] → [Save state] → [Events/outside integration] → [Observe and recover]

CHAPTER 02

Step-by-Step Design Process

1

Define problem

Define the use case's invariants and final state.

2

Pull out the structure

Put only DB changes that must be atomic in a transaction.

3

Core design

Choose a lock strategy based on how often things are edited at the same time.

4

Failure conditions

Put connect/response timeouts and limited retries on outside calls.

5

Link policies

Apply idempotency and compensation to duplicate messages and partial failures.

6

Check and trace

Link logs, metrics and distributed traces with a correlation ID.

A working example

Optimistic lock pseudocode
UPDATE inventory SET quantity = quantity - 1, version = version + 1 WHERE product_id = :id AND quantity > 0 AND version = :expectedVersion; -- if affected rows = 0, it's sold out or a concurrent update conflict

What to check when reading the example

  • Are the input and start condition clear?
  • Are failure results observable, not just normal ones?
  • Are duplicates, permissions, concurrency and external failures covered enough?
  • Can requirements and build results be traced to each other?

CHAPTER 04

Combined Lab and Model Answers

Assignment

Design the flow when 100 orders come in at once for a product with 1 left in stock. Also handle a stock save failure after payment succeeds.

  1. Write key assumptions and undecided items first.
  2. Write the main design outputs as tables, code or diagrams.
  3. Include the normal flow and at least 3 failure/boundary conditions.
  4. Score with the self-check table and compare before and after.
Show the model answer's key direction

Let only one request succeed in reducing stock with a conditional UPDATE or row lock. Use an idempotency key for order requests. If confirming stock fails after payment, publish a payment cancellation event and save the result in a traceable state.

How to use the answer

The model answer isn't the only right answer. If your design differs, you should be able to explain which reason — requirements, cost, complexity or risk — led you to a different choice.

SELF-STUDY 02

Guided Lab and Troubleshooting

Lab situation

On order creation, reduce stock, request payment, then send an email asynchronously.

Do in order

  1. Write business invariants and the state that must be kept on failure.
  2. Separate the boundary between DB transactions and outside calls.
  3. Sort errors into retryable ones and ones that should fail right away.
  4. Add request IDs, structured logs and key metrics, then recreate the failure.
Evidence to keep

Save 1 output, 3 key assumptions and 3+ failure cases. Another learner should be able to repeat your reasoning without asking more questions.

Diagnose when results differ

Symptom seenPossible causeNext action
Stock goes down but there's no orderWrong transaction scopeHandle order and stock changes atomically
An email failure makes the order fail tooFollow-up work tightly coupledPublish to a queue after the order is confirmed
Hard to find the cause of failuresNo correlation IDRecord the request ID and results of each step

SELF-STUDY 03

Check Your Own Understanding

Recall practice — answer before opening

Why is it risky to wait for an outside payment inside a DB transaction?

Lock time gets longer, throughput drops, and failures are more likely to spread.

What is cache invalidation?

A policy that deletes or refreshes stale cache when the source data changes.

What's the done criterion for the back end?

Business rules, failure recovery, security and observability must be proven with tests.

Teach it in 2 minutes

Without looking at the page, explain today's key judgment, a typical failure cause and how to check it, linked together. If the three don't connect, go back to the terms or diagnosis cases you missed.
