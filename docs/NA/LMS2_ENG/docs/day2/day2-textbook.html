CHAPTER 01

Core Theory of Sequence Diagrams and Data Flow Design

Technical terms look complex, but each exists to solve one problem that keeps coming up in design. In the table below, focus on "when is it needed" more than "what does it mean."

Key conceptExplanation
LifelineThe timeline of an object in the interaction, like a user, screen, service or DB.
MessageA request and response between objects. The direction and order of calls are key.
ActivationThe span where an object is actually doing work.
Combined FragmentShows conditional branches (alt), options (opt), loops (loop) and parallel (par).
BoundaryThe screen or API boundary that touches users or external systems.
Control / EntityThe logic that coordinates business flow, and persistent data, respectively.

The difference between good and bad design

Approach to avoid

Show all internal responsibilities as one "system," like user → system → DB.

Recommended approach

Separate responsibilities and failure points: user → booking screen → booking service → payment gateway → DB.

Design formula

[Start condition] → [Participating objects] → [Sync/async messages] → [State change] → [Response or compensation]

CHAPTER 02

Step-by-Step Design Process

1

Define problem

Mark the user goal and start condition in the requirement.

2

Pull out the structure

Pull out screens, services, external APIs and data stores as participating objects.

3

Core design

Lay out the normal flow in time order and separate requests from responses.

4

Failure conditions

Add failures, timeouts and duplicate requests as alt blocks.

5

Link policies

Link lock, version and idempotency policies to resources accessed at the same time.

6

Check and trace

Trace requirement IDs and API/table names in the diagram.

A working example

Mermaid sequence diagram example
sequenceDiagram actor User as User participant UI as Booking screen participant API as Booking service participant PG as Payment service participant DB as Booking DB User->>UI: Choose seat and time UI->>API: Booking request(idempotencyKey) API->>DB: Check seat availability API->>PG: Request payment approval alt Payment succeeds PG-->>API: Approval number API->>DB: Confirm booking API-->>UI: Booking done else Payment fails PG-->>API: Failure reason API-->>UI: Retry message end

What to check when reading the example

  • Are the input and start condition clear?
  • Are failure results observable, not just normal ones?
  • Are duplicates, permissions, concurrency and external failures covered enough?
  • Can requirements and build results be traced to each other?

CHAPTER 04

Combined Lab and Model Answers

Assignment

Design a sequence where two users book the same seat at the same time. Include the case where saving to the DB fails after payment succeeds.

  1. Write key assumptions and undecided items first.
  2. Write the main design outputs as tables, code or diagrams.
  3. Include the normal flow and at least 3 failure/boundary conditions.
  4. Score with the self-check table and compare before and after.
Show the model answer's key direction

The booking service must lock the seat row or check a version value, then let only one request go to payment. If payment succeeds but saving the booking fails, call a compensating transaction (cancel approval or refund) and leave an operations alert.

How to use the answer

The model answer isn't the only right answer. If your design differs, you should be able to explain which reason — requirements, cost, complexity or risk — led you to a different choice.

SELF-STUDY 01

Key Terms in Context

Don't just memorize definitions; learn terms as decision tools. Read each row as definition → why it's needed → example or caution.

TermSimple definitionWhy it mattersExample or caution
Sync callCommunication where the caller waits for a response before the next taskGood for lookups and checks that need an immediate resultIf the external API is slow, the whole request is slow.
Async eventSends a request without waiting, and delivers the result as an eventLowers coupling for notifications, logs and follow-up processingYou must set processing order and duplicate consumption policies separately.
IdempotencyRunning the same request many times gives the same final result as running it oncePrevents double payments and double bookings on retryStore the request key and reuse the earlier result.
Race conditionA problem where results depend on the order of tasks running at the same timeEssential for limited resources like stock and seatsWrap the check and update in one transaction.
TimeoutA rule that ends a call as failed if there's no response within a set timePrevents endless waiting and resource exhaustionDesign the retry count and user message too.
CompensationFollow-up work that cancels the effect of an earlier step that already succeededRecovers from partial failure across distributed servicesCancel the approval when payment succeeds but booking fails.

SELF-STUDY 02

Guided Lab and Troubleshooting

Lab situation

Two users book the last seat at the same time, and saving to the database fails once right after payment approval.

Do in order

  1. Write the Actor, screen, booking service, payment service and DB as lifelines.
  2. Draw the normal flow first and write the input and return value on each message.
  3. Separate simultaneous requests, payment rejection and save failure into alt blocks.
  4. Show which object owns the idempotency key, seat lock and compensating payment.
Evidence to keep

Save 1 output, 3 key assumptions and 3+ failure cases. Another learner should be able to repeat your reasoning without asking more questions.

Diagnose when results differ

Symptom seenPossible causeNext action
A seat is sold twiceAvailability check and deduction are separateRow lock or conditional update
Payment is approved twiceA retry is treated as a new requestIdempotency key and stored result
The screen keeps waitingNo timeout on external callsDefine timeout, retry and failure response

SELF-STUDY 03

Check Your Own Understanding

Recall practice — answer before opening

What's the difference between alt and opt?

alt picks one of several conditions; opt runs its section only when the condition is true.

Why cancel the payment after a DB save fails?

To fix the mismatch where money was taken but there's no booking.

What's the done criterion for a diagram?

Normal, failure and recovery flows, with each responsibility linked to a build element.

Teach it in 2 minutes

Without looking at the page, explain today's key judgment, a typical failure cause and how to check it, linked together. If the three don't connect, go back to the terms or diagnosis cases you missed.
