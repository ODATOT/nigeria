What is gstack?

gstack = a set of role-based work guides for AI agents

An open-source skill set released by Y Combinator CEO Garry Tan (github.com/garrytan/gstack). It splits one AI into CEO, designer, engineer, reviewer and QA roles.

Where does gstack live?

gstack is not an app — it's a work manual AI reads

When you install it, a folder of guides appears on your computer, and the AI tool picks the guide that matches your command and follows it.

One AI · Five hats

3 Principles

Today you learn a way of working, not just commands

01Don't build right awayBefore code, confirm the user problem and scope, and bring hidden assumptions to light."Whose pain does this solve, and what pain?"
02Split rolesRun product, design, tech, review and QA views as separate skills, without mixing them.No code changes during planning
03Verify resultsAI output is not an answer key. People check it with files, git diff and running it in the browser.No pass without evidence

Day 3 · Part 2 · Document-driven design

From conversation to spec,
from spec to service.

Organize requirement conversations into Markdown contracts people can review, check them with gstack, and build using only those documents as the basis.

01 · Sort the conversationFACT · QUESTION · DECISION25 pts · 3–4h
02 · Design the specUX · DATA · API · QA25 pts · 4–6h
03 · Build the serviceBUILD · TRACE · TEST30 pts · 6–9h (advanced)
04 · Verify design & serviceVERIFY · EVIDENCE · RETRO20 pts · 3–5h (advanced)
Why documents?

A doc is not a report — it's a build contract with AI

Developing by chat only

  • Requirements are scattered across chat history
  • AI fills the blanks as it likes (assumptions become facts)
  • Customer and admin screens don't share the same data
  • Nobody can judge "what counts as done"

Document-based development

  • Every requirement has an ID linked to screens, data and tests
  • Facts, assumptions and decisions are separated, so guesses show up
  • Both screens share a common data contract
  • PASS/FAIL is judged by acceptance criteria

How to write a screen spec

One screen = purpose · info · actions · next state · acceptance criteria

## UI-C03 — Menu detail · choose options  (REQ-004, REQ-005)
- Purpose: customer picks bread, sauce and size and sees the final price
- Info shown: menu name, description, base price, option groups (required/optional), live total
- Actions: choose options, quantity +/-, [Add to cart]
- Next state: added → toast + cart badge goes up (UI-C04)
- States: normal / sold out (add button disabled) / required option not chosen (message) / save failed (retry)
- Acceptance criteria:
  - Given required option not chosen When [Add] Then not added + "Please choose bread" shown
  - Total = (base_price + option extras) × quantity

Verify documents with gstack

Cross-audit prompt

/plan-eng-review
Cross-review the service-planning, service-analysis
and service-validation documents.
Don't add new requirements; only find:
1. Mismatched terms, IDs and order status values
2. Features on screens with no DATA/API
3. Vague done criteria that can't be measured
4. Privacy, payment and permission risks, and questions people must decide
Don't change any files.

Design verification check

  • Terms, REQ IDs, status values and field names match in every doc
  • Every key REQ links to acceptance criteria and a TEST
  • Data flow is unbroken from customer order creation to admin status change
  • No missing permissions, privacy exclusions or exception handling
  • Record the accept / change / reject reason for every AI finding
