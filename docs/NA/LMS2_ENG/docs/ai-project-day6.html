Opening question

Why do services fail?
Not "couldn't build it" but "nobody wanted it"

A common start

  • "It'd be cool to build this app with AI"
  • Write a feature list first
  • Draw screens first and pick a tech stack
  • Users are "everyone"

A start that survives

  • "Who struggles, when, and because of what?"
  • Observe how that person copes today
  • Start with the single narrowest user
  • Define success in numbers
In analyses of startup failure, "no market need" is always a top cause. AI speeds up building — and also speeds you up in the wrong direction.
Analogy · Market stalls

Not the best-made stall, but the stall where it's needed survives

What matters most

The 5 most important things in a project

1Problem firstStart from users' pain, not features
2Narrow userNot "everyone" but the one who needs it most
3Small scopeAn MVP where one key action works end to end
4Verifiable criteriaNumbers and acceptance criteria, not "make it good"
5People judgeRecord accept/change/reject of AI suggestions and why
One flow that fully solves one user's problem is a stronger demo — and a better product — than 10 flashy features.
Why · validate the problem

Validate a problem with past behavior, not opinions

Bad questions (invite compliments)

  • "Would you use an app like this?"
  • "What do you think of this idea?"
  • "Would you pay for it?"

Future promises and compliments are not evidence.

Good questions (invite facts)

  • "When did you last have this problem? How did you solve it?"
  • "What took the longest in that process?"
  • "Have you already spent money or tried something to solve it?"
Make something people want. — Y Combinator · Ask about their life, not your idea. — The Mom Test
What · define the MVP

Lock the What with 3 sentences · a scope table · success metrics

3-sentence definition① Purpose: students check in with a QR code and the teacher sees it live
② Student: search name → pick card → scan QR → checked in
③ Teacher: dashboard → live update → filter absenteesDoes the whole team picture the same product?
Must / Should / OutMust: save attendance, update status
Should: late mark, filters
Out: login, location check, stats reportCan you say what you're NOT building?
Success metricsStudents check in within 30 seconds
Teacher sees absentees within 10 seconds
0 duplicate check-insCan you prove it with numbers in the demo?
MVP = thinnest complete slice

An MVP isn't the whole thing done roughly but one small, finished slice

Building layer by layer

Day 1: 10 empty screen shells
Day 2: all DB tables
Day 3: all APIs
Day 4: connecting... doesn't work
Day 5: no flow to demo

Slicing vertically

Slice 1: student check-in → save → shows on dashboard
         (screen, data and logic all included, working)
Slice 2: duplicate/expiry exception handling
Slice 3: filters · late mark
→ a working demo every day
Every evening you need at least one "flow you can demo right now". That's the rhythm of an MVP sprint.

MVP = a vehicle you can ride at every stage

PLAN · scope & engineering review

Lock the plan: scope with the CEO review, structure with the engineering review

/plan-ceo-review · 4 modes

  • Scope Expansion — dream big
  • Selective Expansion — add selectively
  • Hold Scope — lock scope, maximum rigor ← default
  • Scope Reduction — keep only the core ← when the schedule is tight

/plan-eng-review

  • Lock data flow and architecture
  • Find exceptions and hidden assumptions (duplicates, expiry, save failure)
  • Test plan per requirement ID → Phase 4 /qa takes it over
  • List contradictions between docs in a table

Short on time? /autoplan: run reviews in one go and receive only the items people must decide

BUILD → REVIEW → TEST → SHIP → REFLECT

Build, doubt, prove, and finish with the docs matching

BuildLimit changes to website/ with /freeze → have AI read the docs first, then build in small unitsExactly the Day 4 way
Review/review — find bugs that break in real use even if CI passes, and builds that differ from the planCheck the diff even for auto-fixes
Test/qa-only report → /investigate cause → /qa fix and re-checkNo PASS for items not run
Ship · ReflectUpdate docs with /document-release → reflect with /retroDocs = site
Change request · Spec-First

Changes go docs first. Changing code first isn't Spec-First

  • First agree on what the request really means ("real time" = refresh? polling? WebSocket?)
  • Put the impact on screens · flows · data · permissions · tests · schedule in a table
  • Don't rebuild everything for one request — a small diff
  • If it's outside the goal, put it in the next version's backlog instead of building it
What is AI Native development?

AI Native = redesigning the process on the assumption you work with AI

AI-assisted (using it as a tool)

  • People decide and write everything; AI only autocompletes
  • Paste the error into chat when stuck
  • Context disappears when the chat ends
  • No review standard — "if it runs, OK"

AI Native (working as a teammate)

  • AI roles in every phase (planning review · build · QA · retro)
  • People focus on define → review → judge
  • Context stays in MD docs and logs for the next AI to pick up
  • Done is judged by the docs' acceptance criteria and test evidence
AI has made typing fast. So people's value shifts to defining what's right and judging whether results are right.
Analogy · Orchestra

AI Native = an AI orchestra conducted by people

Each team member gets decisions they own and a paired AI

A day in an AI Native team

Daily rhythm: decide small, build small, show it every day

Small batchesOne REQ = one plan = one commit. Reject big diffs you can't review
Integrate dailyDon't keep branches separate for long; merge at least once a day
Demo dailyEvery evening, demo a flow that really works to the team and mentor
Evidence over demo

Record and show the reasons for your decisions, more than results

gstack · AI Prompts by Phase

Fill the [brackets] and paste into Codex or Antigravity chat.

[THINK] /office-hours
We want to build a service that solves [problem] for [users] in 5 days.
Ask us questions based on the 3-sentence definition and interview notes below,
and point out the riskiest assumption and the narrowest starting scope.
[paste 3-sentence definition + interview summary]

[PLAN] /plan-ceo-review
Review SITE_SPEC.md in Hold Scope mode. Suggest features that can't be demoed
in 5 days as candidates to move to Out, and tell us if any core value is missing.

[PLAN] /plan-eng-review
Review the 5 planning docs, list contradictions between docs, hidden assumptions and missing exception flows in a table,
and create a test plan for each requirement ID (FR-xxx).

[BUILD] Build request (Codex · Antigravity)
Read the 5 planning docs first and propose only the build plan for FR-[ ].
Show the files to create or change and why, and the acceptance criteria to check; build after approval.

[REVIEW] /review
Review the website/ code against SITE_SPEC's requirement IDs and acceptance criteria.
Look first for features not in the plan, and unhandled save failures and double clicks.

[TEST] /qa-only
Run the TEST_PLAN.md scenarios in the browser; don't fix any code,
and leave reproduction steps and screenshots for each defect.

[REFLECT] /retro
Using CONVERSATION.md and the work history, summarize what went well, what was hard,
cases where we rejected or changed AI suggestions, and 1 improvement for the next version.
Don't add achievements without evidence.
