Why frameworks?

Framework = repeated work + agreements on where code goes

Without a framework

  • Build URL parsing, DB connections, sessions and security yourself every time
  • Code location and style differ from person to person
  • Risk of security mistakes like SQL injection and CSRF

With a framework

  • Routing · ORM · auth · admin · security built in
  • Shared structure: "models here, views here" → easier teamwork
  • Easier for AI to write code in the right place too
A library is a tool you call; a framework is a skeleton that calls you. (Inversion of control)

Dependency rule

Dependencies flow one way only

apps / APIView · Serializer — validate HTTP requests, call the Workflow
↓ calls
business / WorkflowCoordinates the whole use-case order
↓ orchestrates
business / Rule · Policy · CalculatorPure business rules · policy decisions · amount calculation (no Django)
↓ depends on interface
business / Port (Protocol)OrderRepository · PaymentGateway interfaces
↑ implements
infrastructure / Repository · AdapterDjango ORM · payment provider API · Outbox implementations

Rule · Policy · Calculator

Day 3 REQs become pure Python rules

Rule · REQ-006

class OrderQuantityRule:
    MAX = 20

    def evaluate(self, quantity):
        if quantity < 1 or quantity > self.MAX:
            return RuleResult.reject(
                "QUANTITY_OUT_OF_RANGE")
        return RuleResult.accept()

Policy

class OrderAcceptancePolicy:
    def __init__(self, rules):
        self.rules = rules

    def evaluate(self, context):
        for rule in self.rules:
            result = rule.evaluate(context)
            if not result.passed:
                return result
        return RuleResult.accept()

Calculator

class OrderPriceCalculator:
    def calculate(self, items):
        return sum(
            item.unit_price * item.quantity
            for item in items
        )
# Use integers (smallest currency unit)
# or Decimal for money; no float

Workflow & dependency injection

The Workflow does only the order; assembly happens in container.py

business/cafe/workflows/create_order_workflow.py

def execute(self, command):
    menus = self.menu_repository.get_available_menus(
        menu_ids=[i.menu_id for i in command.items])
    self.acceptance_policy.validate(
        menus=menus, items=command.items)
    total = self.price_calculator.calculate(
        items=command.items, menus=menus)
    with self.unit_of_work:
        return self.order_repository.create_order(
            customer_id=command.customer_id,
            items=command.items, total_price=total)

3-level test strategy

When layers split, tests split too

Check business rules fast with Unit tests without a DB; check DB and provider connections with higher-level tests.

AI development spec

12-step order · 9 don'ts for AI agents

Build order

Never do this

  • Complex business logic in the View
  • Using the Django ORM in business
  • Copying without checking existing Rules
  • Returning the provider's raw response as-is
  • Fixing a bug with a quick if-statement and no failing test
  • Changing existing Migrations · hard-coding Secret Keys
  • Large unrequested refactoring · reporting tests passed that were never run
Wrap-up

Not adding folders, but containing the impact of change

If this changesOnly this changes
API spec changeapps/<domain>/api
Business rule changebusiness/<domain>/rules · policies
Price formula changebusiness/<domain>/calculators
DB access method changeinfrastructure/repositories
Add · change payment providerinfrastructure/payment_gateways/<provider>
  • The View takes requests and calls the Workflow
  • The Workflow manages the business process order
  • Rule · Policy · Calculator are pure business logic
  • DB and outside systems connect via Ports and Adapters; business doesn't depend on Django
