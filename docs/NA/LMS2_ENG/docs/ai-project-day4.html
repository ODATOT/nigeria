Opening question

"Antigravity, build me an ordering kiosk."
Will you get the same app yesterday and today?

Developing by chat only

  • Structure, names and colors change with every request
  • A new chat forgets earlier decisions
  • It adds features you didn't ask for "on its own"
  • No standard to judge what's right

Developing with MD docs

  • AGENTS.md injects the same rules into every chat
  • IDs in spec MDs lock the scope exactly
  • Decisions stay in DECISION_LOG for the next AI to read
  • "Done" is judged by acceptance criteria
AI's memory lives in the file system, not the chat window. A decision you didn't record is a decision that doesn't exist for the AI in the next chat.

Size limits

Rule activation · trigger

Design rules down to when they get read

If every rule is always_on, important rules get buried. Choose the trigger by asking "Is it always needed?"

always_onAlways appliedInjected in full in every chat. Only short, absolute rules, like docs-first and don'ts.e.g. doc-contract.md
globFile patternApplied automatically only when handling certain files, like globs: **/*.css, **/styles/**.e.g. frontend-style.md
model_decisionAI decidesOnly the description shows first; AI reads the whole thing when the task fits.e.g. safety.md (personal data · payment)
manualOnly when @mentionedIncluded only when you call it directly in chat, like @release-check.e.g. release-check.md

              Good spec vs vague spec
              
A spec AI can build = ID + rules + states + acceptance criteria

              

              

                
 Vague spec
## Cart
- You can change quantity conveniently
- The total is shown
- It tells you if there's an error
  • AI interprets "conveniently" however it likes
  • No max quantity, empty state or failure state
  • No standard to judge done

                
 Buildable spec
## REQ-004 Cart quantity · total (UI-C04)
- Quantity: 1–10; at 0, confirm deletion
- Total = Σ(base price + option extras) × quantity
- States: normal / empty cart / contains sold-out / save failed
- AC-1 Given empty cart When open
       Then order button disabled + reason text
- AC-2 Given contains sold-out item Then warning on that row
- Verification: TEST-006, TEST-007

              How to add an MD · 5 steps
              
A new MD must go through 5 steps to become AI's standard

              

                
① Choose layerRule, spec, log or procedure? Add to an existing doc or make a new one?

                
② Template + IDCopy the template and give a unique ID like REQ-011 or UI-C09

                
③ Register in mapAdd the path to the AGENTS.md doc map and TRACEABILITY.md

                
④ AI cross-auditCheck for term, ID and status contradictions and gaps with existing docs

                
⑤ Approve · commitA person reviews and fixes, then confirms with a docs: commit

              

              
Skip ③ and the doc exists but AI doesn't know it's there. Adding means registering too.

# [Service name] — AGENTS.md

## 1. One-line definition
[Customers] [order sandwiches and drinks] on [mobile],
and [the admin] manages [order status and sold-out items] on [PC].

## 2. Doc map (question → doc to read)
- Scope · decisions → PROJECT_BRIEF.md, DECISION_LOG.md
- Customer screens · flows → service-planning/customer-order/*.md
- Admin screens → service-planning/admin/*.md
- Shared policy · order status values → service-planning/common/service-policies.md
- Design → service-planning/design-concept.md
- Metrics · events → service-analysis/*.md
- Verification · test data → service-validation/*.md
- ID links → TRACEABILITY.md

## 3. Tech stack · run
- HTML/CSS/Vanilla JS, no build step
- Run: npx serve service-implementation
- Shared data: service-implementation/shared/store.js

## 4. Way of working
- Handle only one requirement ID at a time.
- Before changing code, first report related doc paths, files to change and unclear points.
- If something different from the docs is needed, don't change the code — propose a doc change first.
- When finished, add one line to AI_WORK_LOG.md.

## 5. Don'ts
- Don't add features, screens or fields not in the docs.
- Don't store real personal data, payment data or API keys.
- Don't copy outside brands' logos, text or images.

## 6. Definition of done
- All acceptance criteria (AC) for the REQ are confirmed in the browser
- 0 console errors, works on 360px mobile / 1280px PC
- TRACEABILITY.md status updated

# Doc Contract Rules

- The only basis for building is the approved MDs in service-planning and service-analysis.
- If a request has no requirement ID, first ask which REQ it is.
- Don't guess values not in the spec; report them as [Question].
- Use the spec's field names and status values as-is in the code.
  (e.g. received / preparing / ready / completed / canceled)

## When something different from the docs is needed
1. Stop without changing code.
2. Propose the difference and reason as a DECISION_LOG.md draft (DEC-###).
3. Show the list of affected REQ·UI·DATA·API·TEST.
4. After human approval, change in the order docs → code.

- Mobile 360px first; the PC admin uses 1280px.
- Buttons at least 44px tall, main actions in thumb reach.
- Show states (sold out · error · required) with color + icon + text together.
- A label for every input, an aria-label for icon buttons.
- Don't skip loading, empty, error and success states.

name: build-req
description: Use when building one requirement ID according to the doc contract. Applies to "build REQ-xxx", "build this feature" and "/build-req" requests.
---
# Per-requirement build procedure

1. In TRACEABILITY.md, find the target REQ's UI·DATA·API·TEST IDs and doc paths.
2. Read only those docs. Report unclear points first as a [Question] list.
3. Write an Implementation Plan.
   - Referenced doc paths / files to change or create / how to check each AC
   - Don't change files before human approval.
4. After approval, build the minimum scope. No refactoring outside scope.
5. Summarize in a table what you confirmed in the browser for each AC.
6. Add one line to service-implementation/AI_WORK_LOG.md.
7. Change that row's status in TRACEABILITY.md to "Built".
8. Suggest a commit message: feat(REQ-xxx): [summary]

Run /doc-audit right after adding an MD or changing a spec.
---
name: doc-audit
description: Use to cross-review planning, analysis and verification MDs for contradictions and gaps. Applies to "audit docs", "check specs" and "/doc-audit" requests.
---
# Doc cross-audit procedure

Don't add new requirements or edit docs — only find problems.

1. Read every MD in the AGENTS.md doc map.
2. Report the following in a table:
   - Mismatched terms · IDs · order status values between docs
   - Features in screen specs with no DATA/API definition
   - REQs missing from TRACEABILITY.md, or REQs with no TEST
   - Done criteria that can't be measured ("convenient", "fast")
   - Privacy · payment · permission · copyright risks and questions people must decide
3. Propose the result as a draft of service-validation/REPORT_DOC_AUDIT.md.
