CHAPTER 01

Core Theory of Service Launch and Final Presentation

Technical terms look complex, but each exists to solve one problem that keeps coming up in design. In the table below, focus on "when is it needed" more than "what does it mean."

Key conceptExplanation
DeploymentThe technical act of installing new code in the runtime environment.
ReleaseThe product decision to open a new feature to users.
Blue-GreenA deployment method that keeps old and new environments side by side and switches traffic.
CanaryA method that limits risk by opening to some users first.
RollbackThe steps to go back to the previous stable version when something goes wrong.
ObservabilityBeing able to understand internal state from logs, metrics and traces.

The difference between good and bad design

Approach to avoid

Tests passed, so deploy to all users at once and have developers handle problems by hand.

Recommended approach

Before deploying, set backups, migrations, health checks, gradual traffic, automatic alerts, rollback conditions and owners.

Design formula

[Release scope] → [Pre-checks] → [Deploy strategy] → [Health check] → [Gradual release] → [Observe·respond·roll back]

CHAPTER 02

Step-by-Step Design Process

1

Define problem

Fix the user value and out-of-scope items for this release.

2

Pull out the structure

Check tests, security, data migration and backups.

3

Core design

Choose Blue-Green or Canary and rollback criteria.

4

Failure conditions

Set metrics and alerts for error rate, latency, traffic and resource saturation.

5

Link policies

Confirm owners and the emergency contact chain at the Go/No-Go meeting.

6

Check and trace

Present in the order problem, user, solution, demo, tech decisions, check results.

A working example

Release Go/No-Go criteria example
GO conditions - Key E2E tests 100% passed - 0 critical/high security defects - DB backup and rollback rehearsal done - At Canary 10%, error rate < 1%, p95 < 500ms NO-GO conditions - Payment or login core flow fails - Data migration recovery steps not checked - No owner, monitoring or rollback permission

What to check when reading the example

  • Are the input and start condition clear?
  • Are failure results observable, not just normal ones?
  • Are duplicates, permissions, concurrency and external failures covered enough?
  • Can requirements and build results be traced to each other?

CHAPTER 04

Combined Lab and Model Answers

Assignment

Assume you're launching a booking service, and write a deployment runbook in 30-minute steps and a 5-minute final talk structure.

  1. Write key assumptions and undecided items first.
  2. Write the main design outputs as tables, code or diagrams.
  3. Include the normal flow and at least 3 failure/boundary conditions.
  4. Score with the self-check table and compare before and after.
Show the model answer's key direction

The runbook includes owners, a backup before starting, deploy commands, health checks, 10%·50%·100% traffic switches, error rate criteria at each step, rollback commands and a user notice. The talk can be: problem 40 sec, user and solution 50 sec, demo 100 sec, tech decisions 50 sec, checks and metrics 40 sec, next steps 20 sec.

How to use the answer

The model answer isn't the only right answer. If your design differs, you should be able to explain which reason — requirements, cost, complexity or risk — led you to a different choice.

SELF-STUDY 02

Guided Lab and Troubleshooting

Lab situation

30 minutes before the final talk, you deployed a new version; the login error rate rose and the outside API for the demo is unstable.

Do in order

  1. Write owners for tests, settings, backups, monitoring and rollback on the release checklist.
  2. Deploy with small traffic and watch error rate, latency and key conversions.
  3. If thresholds are crossed, roll back right away and record changes and evidence.
  4. Practice the talk in the order problem → user flow → measured results → next steps.
Evidence to keep

Save 1 output, 3 key assumptions and 3+ failure cases. Another learner should be able to repeat your reasoning without asking more questions.

Diagnose when results differ

Symptom seenPossible causeNext action
Settings errors only in productionEnvironment differences and not enough checksCheck required settings at startup
Failures found late after deployingNo key metrics or alertsAlerts on error rate, latency and conversion
Outside API fails during the demoNo fallback pathChecked demo data and a recorded backup

SELF-STUDY 03

Check Your Own Understanding

Recall practice — answer before opening

What's the difference between a release and a deployment?

Deployment puts code into an environment; release is the decision to show a feature to users.

Why make a rollback plan before deploying?

During an outage there's no time to think, so you need checked recovery steps and owners in advance.

What's the done criterion for the talk?

The audience must clearly understand the problem, core user flow, evidence and next actions.

Teach it in 2 minutes

Without looking at the page, explain today's key judgment, a typical failure cause and how to check it, linked together. If the three don't connect, go back to the terms or diagnosis cases you missed.
