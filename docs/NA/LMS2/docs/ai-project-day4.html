Opening question

“Antigravity야, 주문 키오스크 만들어 줘.”
어제와 오늘, 같은 앱이 나올까요?

대화로만 개발할 때

  • 요청할 때마다 구조·이름·색이 바뀐다
  • 새 대화를 열면 앞에서 정한 결정을 잊는다
  • 요구하지 않은 기능을 “알아서” 추가한다
  • 무엇이 맞는지 판단할 기준이 없다

MD 문서로 개발할 때

  • AGENTS.md가 매 대화에 같은 규칙을 주입한다
  • 명세 MD의 ID로 범위를 정확히 잠근다
  • 결정은 DECISION_LOG에 남아 다음 AI가 읽는다
  • 수용 기준으로 “완료”를 판정한다
AI의 기억은 대화창이 아니라 파일 시스템에 있습니다. 남기지 않은 결정은, 다음 대화의 AI에게 존재하지 않는 결정입니다.
Why Markdown?

MD는 사람과 AI가 함께 읽는 유일한 계약서

둘 다 읽는다제목·표·체크리스트 구조를 사람도 AI도 똑같이 이해

콕 집어 준다채팅에서 @order-flow.md처럼 정확한 문서를 지정

The 3-layer MD stack

프로젝트 MD는 3계층 + 1로 나눕니다

1층 · 규칙 (Rules)항상 적용 — AGENTS.md · .agents/rules/*.md · 전역 ~/.gemini/GEMINI.md → “어떻게 일할 것인가”
2층 · 명세 (Specs)service-planning/ · service-analysis/ — 화면·정책·데이터·API·지표 → “무엇을 만들 것인가”
3층 · 기록 (Logs)DECISION_LOG · AI_WORK_LOG · TRACEABILITY → “무엇을 했고 왜 그렇게 결정했나”
+1 · 절차 (Skills).agents/skills/이름/SKILL.md — 반복 작업 레시피 → /이름으로 호출
새 MD를 만들기 전에 먼저 묻습니다. “이 내용은 규칙인가, 명세인가, 기록인가, 절차인가?” 층을 잘못 고르면 AI가 엉뚱한 때에 읽거나 아예 읽지 않습니다.

전역 규칙 (모든 프로젝트)

  • ~/.gemini/GEMINI.md 또는 ~/.gemini/AGENTS.md
  • ~/.gemini/config/rules/*.md
  • 예: “항상 한국어로 답하고, 코드 주석은 영어로”

크기 한도

  • → 규칙은 짧게, 긴 내용은 명세 MD로 링크
Rule activation · trigger

규칙은 언제 읽힐지까지 설계합니다

모든 규칙을 always_on으로 두면 중요한 규칙이 묻힙니다. “항상 필요한가?”를 기준으로 trigger를 고르세요.

always_on항상 적용매 대화마다 전체 내용이 주입됩니다. 문서 우선 원칙, 금지 사항처럼 짧고 절대적인 규칙만.예: doc-contract.md
glob파일 패턴globs: **/*.css, **/styles/** 처럼 특정 파일을 다룰 때만 자동 적용됩니다.예: frontend-style.md
model_decisionAI가 판단설명(description)만 먼저 보이고, 작업이 맞으면 AI가 스스로 전체를 읽습니다.예: safety.md (개인정보·결제)
manual@멘션할 때만채팅에서 @release-check처럼 직접 부를 때만 들어갑니다.예: release-check.md
AGENTS.md = project constitution

AGENTS.md에는 6개 블록만 씁니다

AGENTS.md (요약)

# 샌드위치 주문 키오스크
고객은 모바일로 주문, 관리자는 PC에서 주문·품절 관리

## 문서 지도
- 화면·흐름 → service-planning/customer-order/*.md
- 관리자 → service-planning/admin/*.md
- 공통 정책·상태값 → service-planning/common/service-policies.md
- 지표·이벤트 → service-analysis/*.md
- 검증 → service-validation/*.md

## 작업 방식
- 요구사항 ID 하나씩, 코드 전에 계획부터
- 문서와 다르면 코드 말고 문서 먼저 제안

6개 블록 체크

  • ① 한 줄 정의 (누가, 무엇을)
  • ② 문서 지도 — 질문별 읽을 MD 경로
  • ③ 기술 스택 · 실행/테스트 명령
  • ④ 작업 방식 (ID 단위 · 계획 우선)
  • ⑤ 금지 사항 (개인정보·복제·임의 기능)
  • ⑥ 완료 정의 (콘솔 에러 0, 360px 등)

명세 MD는 자동으로 읽히지 않습니다. 문서 지도가 AI의 길잡이입니다.

Good spec vs vague spec

AI가 구현할 수 있는 명세 = ID + 규칙 + 상태 + 수용 기준

모호한 명세

## 장바구니
- 편리하게 수량을 바꿀 수 있다
- 합계가 보인다
- 오류가 나면 알려 준다

  • 최대 수량·빈 상태·실패 상태 없음

How to add an MD · 5 steps

새 MD는 5단계를 거쳐야 AI의 기준이 됩니다

① 층 결정규칙·명세·기록·절차 중 어디? 기존 문서에 추가할지 새로 만들지
② 템플릿 + ID템플릿 복사 후 REQ-011, UI-C09 같은 고유 ID 부여
③ 지도에 등록AGENTS.md 문서 지도와 TRACEABILITY.md에 경로 추가
④ AI 교차 감사기존 문서와 용어·ID·상태값 모순과 누락을 검사
⑤ 승인 · 커밋사람이 검토·수정 후 docs: 커밋으로 확정
③을 빼먹으면 문서는 있어도 AI는 그 문서가 있는지 모릅니다. 등록까지가 추가입니다.

Doc drift warning

코드만 고치면, 다음 AI는 옛 문서를 믿습니다

① 기록차이와 이유를 DECISION_LOG에 DEC-### 로 남김
② 영향 분석관련 REQ · UI · DATA · API · TEST를 AI에게 찾게 함
③ 문서 수정service-planning 원본 명세를 먼저 수정
④ 승인학생·팀이 변경을 검토하고 승인
⑤ 코드 · 재검증그 다음에 코드 수정, 테스트 재실행
이 5단계를 doc-contract.md 규칙에 넣어 두면, 문서와 다른 구현이 필요할 때 AI가 스스로 멈추고 먼저 물어봅니다.

Rules vs Skills

  • Rules: 항상 지킬 원칙 (짧게)
  • Skills: 특정 작업의 단계별 레시피 (필요할 때만 로드)
