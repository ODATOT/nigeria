POC 발표는 7분 · 4장면

데모가 중심입니다. 슬라이드는 최소로.

1분 · 문제누구의 어떤 불편인가
3분 · 라이브 데모한 명의 사용자 이야기로
2분 · 만든 과정문서 → AI → 검증, AI가 틀렸던 것
1분 · 다음 단계피드백 요청 + 내일까지 개선
Analogy · 날리우드 장면처럼

데모 스크립트 만들기 

우리 프로젝트의 PROJECT_BRIEF.md, USER_FLOW.md, 최근 QA 결과를 바탕으로
7분 POC 발표용 DEMO_SCRIPT.md 를 만들어 줘.
- 1분 문제 / 3분 라이브 데모 / 2분 만든 과정(문서 → AI → 검증) / 1분 다음 단계
- 데모는 한 명의 사용자 이야기(이름 · 상황)로, 클릭 순서를 번호로
- 실패 상황 1개(오류 · 품절 등)를 보여 주는 장면 포함
- 각 장면에 말할 문장 1~2개, 데모가 멈출 때의 백업 방법
과장된 표현이나 확인되지 않은 수치는 넣지 마.

피드백 분류와 개선 계획 

아래는 POC 발표에서 받은 피드백 목록이다.
각 항목을 Must(최종 발표 전 필수) / Should / Later 로 분류하고,
결함(DEF)인지 요구사항 변경(REQ)인지 구분해 줘.
Must는 최대 3개로 제한하고, 각각
1) 관련 REQ/DEF ID 2) 수정할 파일 예상 3) 재검증 방법 을 제안해 줘.
분류의 최종 결정은 우리가 할 거야. 코드는 수정하지 마.
