What a backend does

백엔드가 하는 6가지 일

① 라우팅URL과 메서드를 보고 어떤 코드가 처리할지 결정/api/v1/cafe/orders → 주문 생성

⑤ 데이터 저장DB에 일관성 있게 기록 (트랜잭션)주문 + 주문 항목 함께 저장
⑥ 외부 연동결제, 문자·이메일 알림, 지도 등실패·지연에 대비
Why frameworks?

프레임워크 = 반복되는 일 + 코드 위치의 약속

프레임워크 없이

  • URL 파싱, DB 연결, 세션, 보안을 매번 직접 구현
  • 사람마다 코드 위치와 스타일이 제각각
  • SQL 인젝션·CSRF 같은 보안 실수 위험

프레임워크와 함께

  • 라우팅 · ORM · 인증 · 관리자 · 보안 기능 기본 제공
  • “모델은 여기, 뷰는 여기” 공통 구조 → 협업 용이
  • AI도 정해진 위치에 코드를 작성하기 쉬움
라이브러리는 내가 부르는 도구, 프레임워크는 나를 불러 주는 뼈대입니다. (제어의 역전)

models.py · Model

class Menu(models.Model):
    name = models.CharField(max_length=50)
    price = models.IntegerField()
    is_available = models.BooleanField(
        default=True)

views.py · Controller

class MenuListView(APIView):
    def get(self, request):
        menus = Menu.objects.filter(
            is_available=True)
        data = MenuSerializer(
            menus, many=True).data
        return Response(data)

urls.py · Router

urlpatterns = [
    path("api/v1/cafe/menus",
         MenuListView.as_view()),
]
Anti-pattern · Fat View / Fat Controller

한 View가 모든 일을 할 때 생기는 문제

책임 6개가 섞인 View

class OrderCreateView(APIView):
    def post(self, request):
        menu = Menu.objects.get(           # DB 조회
            id=request.data["menu_id"])
        if not menu.is_available:          # 업무 규칙
            raise ValidationError("판매 중 아님")
        total = menu.price * \
            request.data["quantity"]       # 계산
        order = Order.objects.create(      # 저장
            user=request.user, total_price=total)
        PaymentAPI.confirm(...)            # 외부 결제
        return Response({"order_id": order.id})

규모가 커지면

  • 같은 규칙이 여러 API에 중복된다
  • DB 없이 업무 로직을 테스트할 수 없다
  • 여러 개발자가 같은 파일을 고쳐 충돌한다
  • 결제사 변경이 서비스 전체에 영향을 준다
  • AI가 코드 위치를 일관되게 판단하지 못한다

Rule · REQ-006

class OrderQuantityRule:
    MAX = 20

    def evaluate(self, quantity):
        if quantity < 1 or quantity > self.MAX:
            return RuleResult.reject(
                "QUANTITY_OUT_OF_RANGE")
        return RuleResult.accept()

Policy

class OrderAcceptancePolicy:
    def __init__(self, rules):
        self.rules = rules

    def evaluate(self, context):
        for rule in self.rules:
            result = rule.evaluate(context)
            if not result.passed:
                return result
        return RuleResult.accept()

Calculator

class OrderPriceCalculator:
    def calculate(self, items):
        return sum(
            item.unit_price * item.quantity
            for item in items
        )
# 금액은 정수(최소 화폐 단위)
# 또는 Decimal 사용, float 금지

def execute(self, command):
    menus = self.menu_repository.get_available_menus(
        menu_ids=[i.menu_id for i in command.items])
    self.acceptance_policy.validate(
        menus=menus, items=command.items)
    total = self.price_calculator.calculate(
        items=command.items, menus=menus)
    with self.unit_of_work:
        return self.order_repository.create_order(
            customer_id=command.customer_id,
            items=command.items, total_price=total)

class PaymentGateway(Protocol):
    provider_code: str
    def confirm(self, command) -> PaymentResult: ...
    def get_payment(self, payment_id) -> PaymentResult: ...
    def cancel(self, command) -> RefundResult: ...
    def verify_webhook(self, raw_body, headers) -> bool: ...

Registry (조립)

class PaymentGatewayRegistry:
    def __init__(self, gateways):
        self._gateways = {
            g.provider_code: g for g in gateways}
    def get(self, provider_code):
        return self._gateways[provider_code]

Payment safety

돈이 오가는 곳의 5가지 안전장치

상태 전이READY → PENDING → PAID / FAILED
PAID → REFUNDED금지: FAILED → REFUNDED
TX 분리TX1: PENDING 저장 → TX 밖: 결제사 호출 → TX2: 결과 + OutboxTimeout ≠ 즉시 실패
멱등성Idempotency-Key 필수. 같은 키 + 같은 요청 → 기존 결과다른 금액 → 409
웹훅Raw Body 서명 검증, event_id Unique과거 이벤트가 최신 상태 덮어쓰기 금지
Outbox결제 저장과 이벤트를 같은 TX에, 후속 작업은 Commit 후 비동기알림 장애 ≠ 결제 롤백
