Opening question

서비스는 왜 실패할까요?
“못 만들어서”가 아니라 “아무도 원하지 않아서”

흔한 출발

  • “AI로 이런 앱 만들면 멋있겠다”
  • 기능 목록부터 적는다
  • 화면을 먼저 그리고 기술 스택을 고른다
  • 사용자는 “모두”

살아남는 출발

  • “누가, 언제, 무엇 때문에 불편한가”
  • 그 사람이 지금 어떻게 버티고 있는지 관찰한다
  • 가장 좁은 사용자 한 명부터 시작한다
  • 성공을 숫자로 정한다
스타트업 실패 원인 분석에서 “시장 수요 없음(no market need)”은 늘 최상위 원인입니다. AI는 만드는 속도를 높이지만, 틀린 방향의 속도도 함께 높입니다.

What matters most

프로젝트에서 가장 중요한 5가지

1문제 먼저기능이 아니라 사용자의 불편에서 출발
2좁은 사용자“모두”가 아니라 가장 절실한 한 사람
3작은 범위핵심 행동 하나가 끝까지 동작하는 MVP
4검증 가능한 기준“좋게”가 아니라 숫자와 수용 기준
5판단은 사람AI 제안의 채택·수정·거절과 이유를 기록
화려한 기능 10개보다 사용자 한 명의 문제를 끝까지 해결하는 흐름 1개가 더 강한 데모이고, 더 좋은 제품입니다.
Why · validate the problem

문제는 의견이 아니라 과거 행동으로 검증합니다

나쁜 질문 (칭찬을 부른다)

  • “이런 앱 있으면 쓸 것 같아요?”
  • “이 아이디어 어때요?”
  • “돈 내고 쓸 의향 있어요?”

미래형 약속과 칭찬은 증거가 아닙니다.

좋은 질문 (사실을 부른다)

  • “마지막으로 이 문제를 겪은 게 언제예요? 어떻게 해결했어요?”
  • “그 과정에서 가장 시간이 오래 걸린 건 뭐예요?”
  • “그걸 해결하려고 이미 써 본 방법이나 돈이 있나요?”
Make something people want. — Y Combinator · 상대의 삶에 대해 묻고, 내 아이디어는 묻지 마라. — The Mom Test
What · define the MVP

What은 3문장 · 범위표 · 성공 지표로 고정합니다

3문장 정의① 목적: 학생이 QR로 출석하고 선생님이 실시간으로 확인한다
② 학생: 이름 검색 → 카드 선택 → QR 스캔 → 출석
③ 선생님: 대시보드 → 실시간 갱신 → 미출석 필터팀 전원이 같은 제품을 상상하는가?
Must / Should / OutMust: 출석 저장, 현황 반영
Should: 지각 표시, 필터
Out: 로그인, 위치 인증, 통계 리포트“만들지 않는 것”까지 말할 수 있는가?
성공 지표학생이 30초 안에 출석 완료
선생님이 미출석자를 10초 안에 확인
중복 출석 0건데모에서 숫자로 증명할 수 있는가?
MVP = thinnest complete slice

MVP는 대충 만든 전체가 아니라 작지만 완성된 한 조각

층별로 만들기

1일차: 화면 10개 껍데기
2일차: DB 테이블 전부
3일차: API 전부
4일차: 연결... 안 됨
5일차: 데모할 흐름이 없음

수직으로 자르기

1조각: 학생 출석 → 저장 → 대시보드 반영
        (화면·데이터·로직 모두 포함, 동작)
2조각: 중복·만료 예외 처리
3조각: 필터·지각 표시
→ 매일 동작하는 데모가 있음
매일 저녁 “지금 당장 시연할 수 있는 흐름”이 하나 이상 있어야 합니다. 그것이 MVP 스프린트의 리듬입니다.

계획은 CEO 리뷰로 범위를, 엔지니어링 리뷰로 구조를 잠급니다

/plan-ceo-review · 4가지 모드

  • Scope Expansion — 크게 꿈꾸기

  • Hold Scope — 범위 고정, 최대 엄격 ← 기본

Change request · Spec-First

변경은 문서 먼저. 코드부터 고치면 Spec-First가 아닙니다

  • 요청의 진짜 의미부터 합의 (“실시간” = 새로고침? polling? WebSocket?)
  • 화면·흐름·데이터·권한·테스트·일정 영향을 표로
  • 요청 하나 때문에 전체를 다시 만들지 않기 — 작은 diff
  • 목표를 벗어나면 구현 대신 다음 버전 백로그로
What is AI Native development?

AI Native = AI와 함께 일한다는 전제로 프로세스를 다시 설계

AI-assisted (도구로 쓰기)

  • 사람이 다 정하고 다 짜면서 자동완성만 AI
  • 막히면 채팅창에 에러 붙여넣기
  • 대화가 끝나면 맥락이 사라짐
  • 검토 기준 없이 “돌아가면 OK”

AI Native (팀원으로 일하기)

  • 모든 페이즈에 AI 역할을 배치 (기획 리뷰·구현·QA·회고)
  • 사람은 정의 → 검토 → 판단에 집중
  • 맥락은 MD 문서와 로그로 남겨 다음 AI가 이어받음
  • 문서의 수용 기준과 테스트 증거로 완료 판정
타이핑은 AI가 빨라졌습니다. 그래서 사람의 가치는 무엇이 맞는지 정의하고, 결과가 맞는지 판단하는 능력으로 옮겨갑니다.

  • 실제 개인정보·비밀 키를 문서와 코드에 넣지 않는다
  • 모든 AI 결과의 수용·수정·거절 이유를 기록한다
Takeaway

Why와 What은 사람이,
How는 사람과 AI가 함께.

AI Native 개발자는 코드를 가장 빨리 치는 사람이 아니라, 올바른 문제를 고르고 AI 팀을 지휘해 증거로 완성하는 사람입니다.

고르는 힘절실한 사용자의 진짜 문제를 고른다
