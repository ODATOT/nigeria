Setup · 15–60 min

설치: 도구 확인 → gstack 등록 → 상태 확인

macOS · Linux · WSL

# 1. 버전 확인
git --version && node --version && bun --version
codex --version   # 또는 claude --version
# 2. gstack 받기 + host 등록
git clone --single-branch --depth 1 \
  https://github.com/garrytan/gstack.git ~/gstack
cd ~/gstack
./setup --host codex   # 또는 --host claude
./setup --status

Windows (PowerShell)

winget install --id Git.Git -e
winget install OpenJS.NodeJS.LTS
powershell -c "irm bun.sh/install.ps1|iex"
git clone --single-branch --depth 1 `
  https://github.com/garrytan/gstack.git "$HOME\gstack"
cd "$HOME\gstack"
.\setup.ps1 --host codex
.\setup.ps1 --status
  • setup.ps1 차단 시: -ExecutionPolicy Bypass -File .\setup.ps1
  • 스킬이 안 보이면: 도구 종료 → 새 터미널 → --status 재확인
Golden rule

AI 작업 전후에는 반드시 git으로 확인

실습 시작 기준점

cd 실습폴더/project
git init
git add .
git commit -m "실습 시작 상태"
# AI 작업 후
git status
git diff

AI 승인 창 4가지 체크

  • ① 지금 실행하려는 것이 git clone / setup 인가?
  • ② 저장소가 공식 garrytan/gstack 인가?
  • ③ 내 홈 폴더 안에서만 작업하는가?
  • ④ 삭제·강제 덮어쓰기 명령이 없는가?
AI의 설명은 실제 파일 · git diff · 브라우저 실행 결과로 검증합니다. 말이 아니라 증거.

Day 3 · Part 2 · Document-driven design

명세를 서비스로.

요구사항 대화를 사람이 검토할 수 있는 Markdown 계약으로 정리하고, gstack으로 검증한 뒤, 그 문서만을 근거로 구현합니다.

01 · 대화 정리FACT · QUESTION · DECISION25점 · 3–4h
02 · 명세 설계UX · DATA · API · QA25점 · 4–6h
03 · 서비스 구현BUILD · TRACE · TEST30점 · 6–9h (심화)
04 · 설계·서비스 검증VERIFY · EVIDENCE · RETRO20점 · 3–5h (심화)
Why documents?

문서는 보고서가 아니라 AI와의 구현 계약

대화로만 개발

  • 요구사항이 채팅 기록 속에 흩어진다
  • AI가 빈칸을 임의로 채운다 (가정이 사실이 됨)
  • 고객 화면과 관리자 화면의 데이터가 어긋난다
  • “무엇이 완료인가”를 아무도 판정할 수 없다

문서 기반 개발

  • 모든 요구에 ID가 있고 화면·데이터·테스트로 연결
  • 사실·가정·결정이 분리되어 추측이 드러난다
  • 공통 데이터 계약을 양쪽 화면이 공유
  • 수용 기준으로 PASS/FAIL을 판정

Mission 01 · Student-first rule

AI를 열기 전에, 내 초안과 질문 5개부터

① 한 문장 정의대상 사용자 · 해결할 문제 · 핵심 행동 · 제외 범위를 내 말로
② 핵심 흐름 초안고객 3~5단계, 관리자 3~5단계를 직접 그린다
③ 모르는 질문 5개예: 품절은 누가, 언제 바꾸나? 주문 취소는 가능한가?
초안이 없으면 AI 결과를 평가할 기준도 없습니다. 결정의 주인은 AI가 아니라 학생입니다.

How to write a screen spec

화면 하나 = 목적 · 정보 · 행동 · 다음 상태 · 수용 기준

## UI-C03 — 메뉴 상세 · 옵션 선택  (REQ-004, REQ-005)
- 목적: 고객이 빵·소스·사이즈를 고르고 최종 가격을 확인한다
- 표시 정보: 메뉴명, 설명, 기본 가격, 옵션 그룹(필수/선택), 실시간 합계
- 행동: 옵션 선택, 수량 +/-, [장바구니 담기]
- 다음 상태: 담기 성공 → 토스트 + 장바구니 배지 증가 (UI-C04)
- 상태: 정상 / 품절(담기 버튼 비활성) / 필수 옵션 미선택(안내) / 저장 실패(재시도)
- 수용 기준:
  - Given 필수 옵션 미선택 When [담기] Then 담기 안 됨 + "빵을 선택하세요" 표시
  - 합계 = base_price + 옵션 추가금 × 수량
