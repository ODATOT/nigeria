# Day 03 교육 내용 요약서 (Codex AI Workspace)

본 요약서는 Day 3 **"기술설계 (데이터 정규화)"** 교육 세션을 진행하는 강사 및 참가자들을 위한 최종 종합 요약 가이드라인입니다. 자연어로 기록된 회의 기록을 물리 데이터 모델(ERD)로 이식하고, 혼란을 초래하는 도메인 용어를 단일 표준 사전으로 단일화하며, 기술적 아키텍처 의사결정과 잠재적인 정합성 위배 Edge Case를 선제 탐색하는 협업 설계 파이프라인의 핵심 요약 정보를 포함합니다.

---

## 📌 Part 1. 도입 배경 및 필요성

### 1. 기술설계의 병목 현상
* **이해 오차**: 동일한 서비스 화면 기획안을 두고 기획자, 디자이너, 개발자가 그리는 데이터 구조 모델과 테이블 설계가 어긋나 결국 데이터 누락 및 정합성 충돌로 귀결됩니다.
* **어휘 오차**: '회원/고객/User/Member' 등 동일 개념에 대해 주체마다 제각기 다른 변수명을 사용하여 개발 및 테스트 시 막대한 용어 정리 비용(Communication Cost)이 낭비됩니다.
* **공유 오차**: 급격한 비즈니스 변경에 맞춰 DB 테이블 스키마만 고치고 API나 화면 설계서를 동기화하지 않아 예기치 못한 시스템 마비가 발생합니다.

### 2. ChatGPT vs Codex Client (Workspace 기반)
| 비교 항목 | ChatGPT (일반 대화형 AI) | Codex Client (Workspace 기반 AI) |
|---|---|---|
| **컨텍스트 인지** | 사용자가 복사해서 붙여넣은 단일 파일/텍스트만 이해함 | 폴더 내 DDL 스키마, DFD, 기획서, API 규격서의 다중 종속 관계를 동시 인지 |
| **용어 표준화** | 일회성 번역에 가까워 전체 코드베이스 단어의 일관성 유지 불가 | 프로젝트 전체 변수 사전을 바탕으로 일관된 표준 네이밍 및 컬럼 추천 |
| **영향 범위 분석** | 단편적인 쿼리 에러 해결 수준에 그침 | 스키마 1줄 변경에 따른 API Endpoint 및 UI 컴포넌트 연쇄 수정 부위 역추론 |

## 📌 Part 3. 따라하기 (Step-by-Step 실습 가이드)

### STEP 1. Task 01 - 데이터 구조 이해 차이 해결
* **행동**: 폴더 내에 `day3_meeting_notes.md` 파일을 작성한 후 프롬프트 창에 아래 명령을 빌드합니다.
  > "제공된 회의록 내용을 데이터 구조 관점에서 분석하여 핵심 엔티티와 관계를 도출하고, 데이터 구조 정의서 및 Mermaid ERD 코드를 작성해 주세요."
* **확인**: 생성된 결과에서 User, Expert, Reservation, Payment 엔티티와 이들의 1:N 및 1:1 카디널리티 관계가 Mermaid 코드로 올바르게 렌더링되는지 확인합니다.

### STEP 2. Task 02 - 용어 표준화
* **행동**: 프로젝트 내의 파편화된 기획/API 문서들을 준비한 후 아래 명령을 빌드합니다.
  > "프로젝트 전반에 혼용되는 '회원/User/고객/Member', '상담사/Expert/선생님/Counselor' 등의 용어를 전수 분석하여, 프로젝트 표준 용어 사전을 Markdown 표 형태로 작성해 주세요."
* **확인**: 한글 표준어에 매핑되는 영문 표준 약어와 추천 DB 컬럼명(`user_id`, `expert_id`)이 사전 형태로 일괄 정의되었는지 점검합니다.

### STEP 3. Task 03 - 변경 영향 공유
* **행동**: 예약 승인 프로세스가 추가된 변경 전/후 스펙을 준비한 뒤 아래 명령을 빌드합니다.
  > "예약 확정 프로세스가 '승인 대기' 상태 추가 및 '전문가 승인 후 결제'로 변경됨에 따라 영향을 받는 API 스펙, DB 스키마, 화면 및 변경 공유 리포트를 작성해 주세요."
* **확인**: 데이터베이스 Reservations 테이블 수정, API 명세서 갱신 대상, 화면 UI 버튼/상태창 수정 요구 사항이 일치되게 도출되었는지 확인합니다.

### Mission 1. 설계 의사결정 기록 (Design Decision Log)
* **행동**: 데이터 이력 분리 및 DDL 쿼리 의결 기록을 준비하고 아래 명령을 빌드합니다.
  > "회의 내용에서 정규화 및 데이터베이스 구조 설계 결정을 추출하여, 결정 항목, 배경 사유, 대안 검토, 승인자, 향후 변경 가능성을 포함하는 Design Decision Log를 작성해 주세요."
* **확인**: 예약 취소 이력 분리 사유(DEC-003)와 대안 기각 논거(대안 1: 테이블 비대화 및 잠금 병목 리스크)가 아카이빙되었는지 점검합니다.

### Mission 2. 예외 시나리오 발굴 (Edge Case Discovery)
* **행동**: 완성된 DB 데이터 모델 스키마를 Codex에 제공하고 아래 명령을 빌드합니다.
  > "현재 정의된 User, Expert, Reservation, Payment 테이블 구조에서 발생할 수 있는 데이터 정합성 위배 Edge Case 예외 시나리오를 도출하고 개선 방안을 제시해 주세요."
* **확인**: 동시 예약 중복 신청(동시성), 탈퇴 회원 이력 유실(참조 무결성), 결제 네트워크 끊김(분산 트랜잭션) 3대 리스크 분류와 Soft Delete 등 구체적 DB 엔지니어링 개선책이 제안되었는지 확인합니다.

## 📌 Part 4. 작동 원리 및 의의

### 1. 스키마 맥락 인지 추론 (Schema Context Awareness)
* 단순 단어 검색이 아닌, 외래키(FK) 참조 관계와 데이터베이스 고유 제약조건의 논리를 파악하여 기획자가 기술한 자연어 흐름(예: 승인 완료 시 예약 확정)을 백엔드 상태 전이 규칙과 DDL 쿼리문으로 형변환하는 원리입니다.

### 2. 메타 용어 클러스터링 (Meta-Terminology Clustering)
* 다중 문서에 파편화된 동의어들을 의미적 군집화(Clustering)하여, 단 하나의 프로젝트 마스터 사전을 도출하고 도메인별 영문 컬럼 룰에 맞게 사전을 자율 학습형으로 빌드해냅니다.

### 3. 다섯 가지 Task/Mission의 기술설계 시너지
```text
[데이터 모델링 합의] (Task 01. 구조화)
         │
         ▼
[도메인 용어 통일] (Task 02. 표준 사전)
         │
         ▼
[설계 변경 영향 추적] (Task 03. 변경 통제)
         │
         ▼
[아키텍처 의사결정 로깅] (Mission 01. Why 보존)
         │
         ▼
[정합성 및 Edge Case 예외 방지] (Mission 02. 안전 설계)
```
이 5단계 협업 루프는 기획 설계 단계에서부터 예외 상황을 원천 봉쇄하여 실제 코딩 작업에 착수하는 개발자들의 생산성을 획득하고 휴먼 에러를 제거하는 데 절대적인 이점을 제공합니다.
