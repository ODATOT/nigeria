# Codex 기반 요구사항 정의 교육 미션 (0단계 ~ 5단계)

이 교육 미션은 비전공자/비개발자가 실제 프로젝트 협업 시나리오를 바탕으로 Codex/ChatGPT AI를 연동하여 기획 요약, 요구사항 정의, 문서 명세화, 기획 질문지 구축 및 최종 문서 통합 & Gmail 플러그인을 활용한 실제 보고 메일 전송까지의 전체 과정을 단계적으로 실습하도록 설계되었습니다.

## 0단계. 상세 대화록에서 핵심 요약 도출 (전처리)

### 미션 상황

기획 회의에서 작성된 회의록 원본은 화자 간의 불필요한 사담, 문맥, 대화 핑퐁으로 인해 요구사항을 즉시 분석하기에 너무 깁니다.
학습자는 Codex를 전처리 도구로 활용하여 회의록에서 핵심 비즈니스 요건만 간략히 요약한 기획 메모를 도출해야 합니다.

### 단계 입력 (Input)
* 비정형 핑퐁 대화 형태의 1차 회의록 원본 ([meeting-notes-raw.md](file:///Users/hojunlee/workspace/ODA_AI_SW/NA/LMS/ai_prompt/meeting-notes-raw.md))

#### 1차 회의 대화록 원본 (`meeting-notes-raw.md`)
```markdown
# 전문가 상담 서비스 구축을 위한 1차 Kick-off 회의록

**일시**: 2026-07-10 14:00 - 15:30
**참석자**: 대표(CEO), 기획자(PM), 개발자(Dev), 디자이너(Designer)

---

**대표**: 여러분, 안녕하세요. 오늘 회의는 우리가 새로 론칭할 "온라인 전문가 상담 서비스"의 기본 요구사항을 논의하고 방향을 잡기 위한 자리입니다. 핵심은 사용자가 우리 플랫폼에 와서 다양한 분야의 전문가를 찾고, 상담 예약을 한 뒤 결제까지 원활하게 마치는 프로세스입니다.

**기획자**: 네, 대표님. 서비스의 기본적인 가입 절차부터 논의를 시작해보죠. 사용자는 회원가입을 해야 서비스를 이용할 수 있는 구조인가요?

**대표**: 네, 맞습니다. 사용자는 우선 회원가입을 마쳐야만 전문가 검색이나 예약 등의 기능을 원활하게 이용할 수 있도록 합시다. 비회원 상태에서는 간단한 둘러보기만 가능하도록 하고요.

**디자이너**: 가입하고 나면 전문가를 검색할 텐데, 전문가 프로필 페이지나 분류 기준은 어떻게 생각하고 계신가요?

**대표**: 전문가는 일단 분야별로 구분되어야 합니다. 예를 들어 IT 컨설팅, 법률 상담, 디자인 코칭 같은 카테고리가 있겠죠. 사용자는 카테고리를 선택하거나 직접 검색어를 입력해 본인이 원하는 전문가를 빠르게 찾아낼 수 있어야 합니다.

**디자이너**: 그러면 검색 결과에서 전문가 목록이 나오고, 상세 페이지로 들어가서 일정을 고르는 구조겠군요. 날짜와 시간은 어떻게 선택하나요?

**대표**: 예, 사용자가 특정 전문가를 선택하면, 해당 전문가가 상담 가능한 스케줄 일정이 캘린더나 타임라인 형태로 표시되어야 해요. 사용자는 그중에서 자신이 상담받고 싶은 날짜와 시간을 자유롭게 골라 예약 신청을 할 수 있게 해야 합니다.

**개발자**: 예약 신청 직후의 결제 프로세스는 어떻게 진행되나요? 예약 신청과 동시에 결제가 바로 이루어져야 예약이 확정되는 형태인가요?

**대표**: 결제가 완료되어야만 최종 예약이 "확정" 상태로 넘어가야 합니다. 만약 PG사 한도 초과나 기타 원인으로 결제가 실패하면, 당연히 그 예약은 완료 처리되면 안 되고 대기 혹은 취소 상태로 묶여야겠죠.

**개발자**: 결제 실패 시 예약이 생성되지 않거나 잠금 해제가 되어야 한다는 비즈니스 규칙이군요. 전문가는 자신이 예약된 스케줄을 어디서 확인하나요?

**대표**: 전문가는 우리 시스템 내에 전문가 전용 대시보드가 있어서, 거기서 자신에게 들어온 예약 신청 내역이나 확정된 스케줄을 실시간으로 모니터링하고 관리할 수 있어야 합니다.

**기획자**: 전문가 가입은 일반 회원가입과 다를 텐데, 인증이나 승인 절차가 별도로 필요한가요? 아무나 전문가로 활동하게 할 순 없으니까요.

**대표**: 좋은 지적입니다. 전문가는 가입 신청을 한 후에 바로 활동할 수 있는 게 아니라, 사이트 관리자가 제출 서류나 자격을 심사한 뒤 "승인"을 해줘야 비로소 전문가 목록에 노출되고 예약 시스템에 참여할 수 있도록 관리자 승인 정책을 필수로 두겠습니다.

**기획자**: 예약을 완료하면 사용자나 전문가에게 알림을 발송해야 개발 편의와 사용성이 높을 텐데, 알림 채널은 어떤 걸 선호하시나요?

**대표**: 알림은 무조건 보내야죠. 예약이 확정되었거나 취소되었을 때 알려줘야 하니까요. 그런데 알림을 이메일로 쏠지, 아니면 휴대폰 문자로 보낼지는 개발 리소스와 비용 문제를 좀 더 따져봐야 할 것 같아요. 이 부분은 아직 확정하지 맙시다.

**개발자**: 취소 수수료나 환불에 대한 규칙도 지금 정해야 하나요?

**대표**: 취소 수수료 정책도 법률 검토와 마케팅 부서 협의가 필요한 사항이라서요. 오늘 당장 결정하긴 어려우니, 이것도 아직 결정되지 않은 보류 사항으로 남겨둡시다. 추후 2차 회의 때 확정 짓는 걸로 하죠.

**기획자**: 알겠습니다. 오늘 결정된 정책과 보류 사항들을 대략 취합해서 명세 초안을 위한 전처리 회의 요약 메모로 정리해 보겠습니다.
```

### 단계 출력 (Output)
* 핵심 요약 메모 파일 ([meeting-notes.md](file:///Users/hojunlee/workspace/ODA_AI_SW/NA/LMS/ai_prompt/meeting-notes.md))

### 학습 목표

* 대화문에서 핵심 요구사항 요건(사용자 역할, 기능 후보, 제약 조건, 미결정 사안)을 골라낸다.
* 대화의 군더더기를 걷어내고 15줄 이내의 정제된 비정형 요약문으로 압축한다.

### 🛠️ 실제 따라 하기 상세 가이드
1. **원본 회의록 확보**: 제공된 예시 대화록 `meeting-notes-raw.md`을 다운로드하여 작업 폴더에 놓거나 파일 내용을 생성합니다.
2. **전처리 지시**: 아래 **Codex 요청 예시** 프롬프트를 복사하여 AI 대화창에 보냅니다.
3. **결과물 저장**: AI가 반환한 정제된 요약 메모 텍스트를 복사하여 `meeting-notes.md` 파일로 저장합니다. 이 파일은 다음 1단계의 입력 데이터가 됩니다.

### Codex 요청 예시 (프롬프트)

```text
meeting-notes-raw.md의 회의록 원문을 읽고, 화자 간의 불필요한 대화 맥락과 문맥을 걷어내고
서비스 사용자, 기능 요건, 시스템 정책, 미결정 유보 사항을 15줄 내외의 컴팩트한 비정형 요약 메모 형태로 작성해줘.
원문에 없는 가상의 내용은 임의로 상상해서 추가하지 말아줘.
```

### 결과 예시 (정제본: `meeting-notes.md`)

```markdown
온라인 전문가 상담 서비스를 만들려고 한다.

사용자는 회원가입 후 전문가를 검색할 수 있다.
전문가는 분야별로 구분한다.
사용자는 상담 날짜와 시간을 선택할 수 있다.
결제가 완료되면 예약이 확정된다.
결제가 실패하면 예약은 완료되면 안 된다.

전문가는 자신의 예약을 확인할 수 있다.
관리자는 전문가 가입을 승인할 수 있다.

예약이 완료되면 알림을 보내야 한다.
알림을 이메일로 보낼지 문자로 보낼지는 아직 정하지 않았다.
취소 수수료 정책도 아직 정하지 않았다.
```

## 1단계. 회의 메모에서 핵심 내용 찾기

### 미션 상황

대표와 기획자, 개발자 등의 회의 대화에서 정제된 0단계의 기획 요약 메모(`meeting-notes.md`)를 분석할 때입니다.
학습자는 이 요약문을 바탕으로 서비스의 주요 객체(사용자 역할, 기능, 비즈니스 룰, 정책)를 정확히 카테고리화해야 합니다.

### 단계 입력 (Input)
* 0단계에서 정제된 요약 기획 메모 파일 ([meeting-notes.md](file:///Users/hojunlee/workspace/ODA_AI_SW/NA/LMS/ai_prompt/meeting-notes.md))

### 단계 출력 (Output)
* 서비스 사용자 역할 목록
* 기능 후보 목록
* 비즈니스 규칙 목록
* 미결정 사항 목록

### 학습 목표

* 회의 메모에서 사용자, 기능, 정책을 구분한다.
* 확정된 내용과 아직 결정되지 않은 내용을 구분한다.
* Codex가 원문에 없는 내용을 임의로 추가하지 않도록 지시한다.

### 🛠️ 실제 따라 하기 상세 가이드
1. **AI에 지시**: 이전 0단계 대화에 이어서 아래 **Codex 요청 예시** 프롬프트를 전송합니다.
2. **분류 결과 분석**: AI가 분석한 사용자가 3개 역할군(Customer, Expert, Admin)으로 구분되었는지 확인합니다.
3. **검증**: 회의 메모에 명시되지 않은 임의의 기능이 분류 결과에 유입되지 않았는지 체크합니다.

### Codex 요청 예시

```text
meeting-notes.md를 읽고 다음 내용을 구분해줘.

1. 서비스 사용자
2. 사용자가 수행하는 기능
3. 시스템이 수행하는 기능
4. 비즈니스 규칙
5. 아직 결정되지 않은 사항

회의 메모에 없는 내용은 추가하지 말고,
불명확한 내용은 별도로 표시해줘.

아직 파일은 수정하지 말고 분석 결과만 보여줘.
```

### 학습자 확인 사항

* 사용자는 Customer, Expert, Admin으로 구분되었는가?
* 결제 성공과 예약 확정의 관계가 확인되었는가?
* 알림 방식과 취소 정책이 미결정 사항으로 분리되었는가?
* Codex가 회의 메모에 없는 기능을 추가하지 않았는가?

## 2단계. 기능 요구사항 문장 만들기

### 미션 상황

1단계에서 분류한 기능 후보군을 활용하여 실제 명세 구조에 준하는 기능 요구사항 문장을 작성할 시간입니다.
개발자와 기획자, QA 등 협업 주체들이 모두 명확하고 동일하게 이해할 수 있는 정형화된 문장 구조로 변환합니다.

### 단계 입력 (Input)
* 1단계 출력물 (사용자 역할 목록, 기능 후보 목록, 비즈니스 규칙 목록, 미결정 사항 목록)

### 단계 출력 (Output)
* `functional-requirements.md` (FR-001 ~ FR-004 규격화된 기능 요구사항 정의서 표)

### 학습 목표

* 기능을 검증 가능한 요구사항 문장으로 작성한다.
* 하나의 요구사항에는 하나의 기능만 포함한다.
* 사용자, 조건, 동작을 포함하여 요구사항을 구체화한다.

### 요구사항 작성 기준

```text
[사용자 또는 시스템]은
[특정 조건]에서
[기능 또는 동작]을 수행할 수 있어야 한다.
```

### 🛠️ 실제 따라 하기 상세 가이드
1. **템플릿 마련**: 작업 공간에 `functional-requirements.md` 파일을 생성하고 아래 **학습자 미션**의 표 형식을 붙여넣습니다.
2. **AI 구조화 의뢰**: 이전 대화에 이어서 아래 **Codex 요청 예시** 프롬프트를 입력합니다.
3. **명세화 및 세이브**: 도출된 명세 표를 복사하여 생성해둔 `functional-requirements.md` 파일에 덮어쓰고 저장합니다.

### 학습자 미션 (템플릿)

```markdown
| 요구사항 ID | 사용자 | 기능명 | 요구사항 설명 |
|---|---|---|---|
| FR-001 | Customer | 회원가입 | |
| FR-002 | Customer | 전문가 조회 | |
| FR-003 | Customer | 상담 시간 선택 | |
| FR-004 | System | 예약 확정 | |
```

### Codex 요청 예시

```text
1단계에서 추출한 기능 후보를 기능 요구사항으로 작성해줘.

다음 규칙을 적용해줘.

1. 요구사항 ID는 FR-001부터 순서대로 부여한다.
2. 하나의 요구사항에는 하나의 기능만 작성한다.
3. 사용자가 누구인지 명확히 작성한다.
4. 기능이 실행되는 조건을 포함한다.
5. 테스트할 수 있는 문장으로 작성한다.
6. "편리하게", "적절하게", "빠르게" 같은 모호한 표현은 사용하지 않는다.
7. 회의 메모에 없는 내용은 추가하지 않는다.

결과는 Markdown 표로 작성해줘.
```

### 결과 예시

```markdown
| 요구사항 ID | 사용자 | 기능명 | 요구사항 설명 |
|---|---|---|---|
| FR-001 | Customer | 회원가입 | 사용자는 회원가입에 필요한 정보를 입력하여 계정을 생성할 수 있어야 한다. |
| FR-002 | Customer | 전문가 조회 | 사용자는 로그인한 상태에서 분야별 전문가 목록을 조회할 수 있어야 한다. |
| FR-003 | Customer | 상담 시간 선택 | 사용자는 전문가를 선택한 상태에서 상담 가능한 날짜와 시간을 조회하고 선택할 수 있어야 한다. |
```

## 3단계. 정상 흐름과 예외 흐름 추가하기

학습자는 주 기능의 정상 플로우와 더불어 비정상 예외 흐름을 함께 보완해 명세서의 완성도를 끌어올려야 합니다.

* 시스템이 예외 상황에서 어떻게 동작해야 하는지 정의한다.

## 5단계. 요구사항 통합문서 생성 및 메일 공유 (Gmail 플러그인)

### 미션 상황

개발 비전공 기획자나 창업가도 코딩 도구의 도움 없이 요구사항 정의서를 하나로 묶고 유효성을 검증하며, 외부 협업 도구와 플러그인을 연결할 수 있어야 합니다.
학습자는 Codex Client의 **Gmail 플러그인**을 직접 설치 및 연동하여, AI 자가 린팅이 완료된 최종 명세 문서 내용을 취합한 보고 이메일을 AI 프롬프트 지시만으로 실제 Gmail을 통해 의사결정권자에게 발송해 봅니다.

### 단계 입력 (Input)
* `meeting-notes.md` (0단계 결과물)
* `functional-requirements.md` (3단계 결과물)
* `open-questions.md` (4단계 결과물)
* Codex Client 내 **Gmail Plugin** 연동 인증

### 단계 출력 (Output)
* `requirements-specification.md` (통합 요구사항 정의서)
* Gmail API 플러그인을 통한 최종 보고 및 승인 요청 메일 발송 완료

### 학습 목표

* AI Client의 외부 확장 플러그인(Gmail) 설치 및 인증 단계를 수행한다.
* AI 자체 린팅 루프로 문서를 최종 통합 검증한다.
* AI에게 이메일 대행 발송 프롬프트를 내려 실제 수신인에게 Gmail을 자동 발송한다.

### 🛠️ 실제 따라 하기 상세 가이드
1. **Gmail 플러그인 연동**:
   * Codex Client의 우측 상단 설정 아이콘이나 플러그인 스토어(Plugins)로 이동합니다.
   * `Gmail` 플러그인을 검색하여 **[설치 (Install)]** 버튼을 클릭합니다.
   * 설치 완료 후, 구글 로그인 OAuth 팝업 창이 열리면 본인의 구글 계정으로 로그인한 뒤 **Gmail 메일 발송 권한을 승인**합니다.
2. **문서 병합 및 1차 검증**: 이전 대화창에 아래 **학습자 미션 1**의 프롬프트를 전송하여 통합 요구사항 정의서 `requirements-specification.md`를 만들어 달라고 요청하고 결과물을 저장합니다.
3. **오류 디버깅**: AI가 검증 피드백 목록을 보여주면 모호성 경고(`WARNING`)나 누락(`ERROR`)을 프롬프트상에서 지시해 문서를 고치고 최종 통과(`PASS`) 상태로 빌드합니다.
4. **Gmail 플러그인 발송 명령**: 아래 **학습자 미션 2 (Gmail 플러그인 발송)** 프롬프트를 AI에 전송하여 AI가 Gmail 플러그인 커맨드를 작동시키도록 지시합니다.
5. **메일 수신 확인**: 지정한 수신인 메일함(혹은 본인의 발송 보낸메일함)으로 AI가 규격화해 쏜 기획 보고 메일이 성공적으로 전송 완료되었는지 확인합니다.
