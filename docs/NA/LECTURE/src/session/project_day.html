Project Day에서는 코덱스에 곧바로 웹사이트를 만들어달라고 요청하는 것이 아니라, 대화로 아이디어를 정리하고 Markdown 문서로 명세화한 뒤 코드를 생성하고 검증하는 6단계 전체 워크플로우를 경험합니다.

Phase 1. 아이디어 구체화 (Idea Definition)
Project Day ACE Startup SW/AI 파일럿
  • 목적: 모호한 아이디어를 생성형 AI에게 곧바로 요청하지 않고 핵심 요소를 3문장 이내로 명확히 정의하기
  • 필수 포함 3대 요소:
    • 사이트 목적: 예) 학생이 QR 코드로 출석하고 선생님이 실시간 출석 현황을 확인하는 웹사이트
    • 사용자(Roles): 학생(카드 선택, QR 스캔), 선생님(현황 모니터링, 필터링)
    • 핵심 행동 & 데이터: 이름/ID 선택, QR 생성, 스캔 및 출석 저장, 상태 실시간 업데이트
  • 실습 지침: Codex 대화창에 세 문장으로 프로젝트의 아이디어와 대상을 명확히 작성해 전달합니다.
생성형 AI는 모호한 아이디어를 자동으로 완성해 주지 않습니다. 아이디어 단계에서 누구를 위한 어떤 사이트인지, 각 사용자의 핵심 행동이 무엇인지 3문장으로 명확히 규정하는 것이 첫 번째 단원입니다.

Phase 2. 기획 문서화 (Markdown Specifications)
Project Day ACE Startup SW/AI 파일럿
  • 문서화의 이유: 사람과 Codex가 모두 오차 없이 읽을 수 있는 표준 명세서 작성
  • 5대 필수 Markdown 문서 팩:
    • SITE_SPEC.md: 사이트 목적, 주요 화면, 완료 기준(Checklist)
    • USER_FLOWS.md: 학생 및 선생님 역할별 단계별 이용 동선
    • DATA_MODEL.md: 학생 정보 및 출석 데이터 구조
    • IMPLEMENTATION_PLAN.md: 구현 순서 및 테스트 계획
    • CONVERSATION.md: 요청/결정/변경 이력 기록지

📁 프로젝트 구조 예시

attendance-project/
├── SITE_SPEC.md
├── USER_FLOWS.md
├── DATA_MODEL.md
├── IMPLEMENTATION_PLAN.md
├── CONVERSATION.md
└── website/
Codex가 일관적인 코드를 짜게 하려면 5대 Markdown 문서 팩을 먼저 완성해야 합니다. 작성 후 직접 열어보며 원치 않는 내용이나 빠진 완료 기준을 검토합니다.

Phase 3. 코덱스 기반 웹사이트 구현 (Implementation)
Project Day ACE Startup SW/AI 파일럿
  • 핵심 구현 지침:
    • 문서 우선 읽기: Codex에게 "작성한 5개 기획 문서를 먼저 전수 읽고 이해했는지 확인해 줘"라고 요청
    • 폴더 분리: 명세 문서 폴더와 웹사이트 실행 코드 폴더(website/)를 철저히 구분
    • 필수 기능 요청: 실제 스캔 가능한 QR 생성, 출석 상태 저장, 선생님 모니터링 화면, 반응형 모바일 레이아웃 반영
  • 프롬프트 예시: "기획 문서를 읽고 website/ 폴더 아래에 학생 출석 QR 페이지와 선생님 모니터링 페이지를 HTML/CSS/JS로 구현해 줘."
구현 요청 시 Codex에게 기존 기획 문서를 먼저 읽도록 지시하는 것이 핵심입니다. 문서와 코드 폴더가 분리되어 있는지, 모바일 반응형 레이아웃이 포함되었는지 확인합니다.

Phase 4. 기능 및 시나리오 테스트 (Testing & Verification)
Project Day ACE Startup SW/AI 파일럿

👨‍🎓 학생 화면 시나리오

  • 이름 검색 ➔ 카드 선택 ➔ 학생별 QR 코드 표시 확인
  • 스마트폰으로 QR 스캔 ➔ 모바일 출석 페이지 접속
  • [출석하기] 버튼 클릭 ➔ 출석 완료 및 시간 표시
  • 예외 테스트: 동일 QR 연타 시 중복 출석 방지 검증

👨‍🏫 선생님 화면 시나리오

  • 전체 출석 현황 모니터링 대시보드 열기
  • 학생이 출석 버튼을 눌렀을 때 실시간 상태 갱신 확인
  • 학생 이름 검색 및 출석/미출석 상태 필터링 테스트
  • 예외 테스트: 네트워크 지연 또는 에러 발생 시 안내 팝업 메시지 확인
학생 역할과 선생님 역할을 나누어 직접 시연합니다. 정상 동작뿐만 아니라 중복 출석 클릭이나 네트워크 오류 등 예외 상황이 기획서의 완료 기준대로 처리되는지 검증합니다.

Phase 5. 피드백 및 사이트·문서 연쇄 개선 (Iterative Refinement)
Project Day ACE Startup SW/AI 파일럿
  • 문서 우선 수정 원칙 (Spec-First Update):
    • 테스트 중 발생한 기능 개선 요청이나 디자인 수정 사항을 코드가 아닌 기획 문서(`SITE_SPEC.md` 등)에 먼저 반영합니다.
    • 예: "선생님 화면에 출석 취소 버튼 추가" ➔ SITE_SPEC.md 및 USER_FLOWS.md에 해당 기획을 먼저 기록
  • Codex 재요청: "SITE_SPEC.md의 변경된 출석 취소 요구사항을 읽고 website/ 코드를 개정해 줘."
  • 교훈: 문서와 코드가 항상 동기화되어 유지되는 선순환 AI 개발 패턴 습득
개선 요청이 있을 때 코드부터 고치는 것이 아니라 문서를 먼저 수정한 뒤 Codex에게 코드 수정을 요청합니다. 이를 통해 기획서와 실제 사이트가 항상 일치하도록 관리하는 습관을 기릅니다.

Phase 6. 작업 이력 기록 및 발표 (History & Presentation)
Project Day ACE Startup SW/AI 파일럿

📝 CONVERSATION.md 작성

  • Codex에 요청한 핵심 프롬프트 내용
  • 개발 중 의사결정 및 선택 이유
  • 발생한 오류와 해결 방법
  • 최종 테스트 검증 통과 결과

🎤 5분 결과 발표 구성

  • 1. 프로젝트 목적 및 핵심 사용자 소개
  • 2. 학생 QR 출석 시연 & 선생님 대시보드 시연
  • 3. 해결하기 가장 어려웠던 에러와 해결 과정
  • 4. **기획 문서를 먼저 쓴 후 개발했을 때의 장점 발표**
마지막 단계에서는 모든 대화 및 결정 이력을 CONVERSATION.md에 기록하고 동료들과 결과를 발표합니다. 기획 문서를 먼저 작성했을 때의 효율성을 직접 발표를 통해 공유합니다.
