AI와 개발 가능한 프로젝트 기획하기

📚 오늘은 코드를 작성하지 않습니다. 완성도 높은 기획 문서(PROJECT.md)가 목표입니다.
이 문서 하나로 Day 3에 Antigravity가 실제 서비스를 만들 수 있습니다.

1. 왜 오늘은 코드를 만들지 않는가?

💬 두 창업팀의 이야기
A팀: "일단 만들어보자!" → Antigravity에게 바로 "반려동물 매칭 앱 만들어줘"라고 요청
→ 결과: 로그인 화면만 나오고 핵심 기능은 없음. 수정 요청을 10번 이상 반복.

B팀: "먼저 문서를 완성하자" → Codex로 PROJECT.md 14섹션을 꼼꼼히 작성
→ 결과: Antigravity가 한 번 요청에 핵심 흐름까지 동작하는 MVP를 생성.

차이: B팀은 오늘(Day 2)을 문서 작성에 투자했습니다.
💡 Day 2 핵심 원칙: 많은 기능보다 하나의 완전한 사용자 흐름을 먼저 설계한다.
Codex가 만든 PROJECT.md 한 파일이 Day 3~5 개발의 모든 기준이 됩니다.

2. 아이디어 vs 문제 정의 — 무엇이 다른가?

기술이나 기능부터 정하면 실제 사용자 문제와 관계없는 제품이 만들어집니다.
좋은 기획은 "누가, 어떤 상황에서, 무엇이 불편해서, 어떻게 해결되길 바라는가"를 명확히 합니다.

📌 문제 정의의 4가지 요소

👤
사용자 (Who)
구체적인 사람. "사람들"이 아니라 "1인 가구 20대 직장인"처럼 좁게 정의
📍
상황 (When/Where)
어떤 순간에 문제를 겪는가? "퇴근 후 집에서 혼자"처럼 구체적으로
😣
불편 (Problem)
지금 어떻게 해결하고 있으며 무엇이 불편한가? 현재 대안의 한계
🎯
원하는 변화 (Goal)
이 문제가 해결되면 어떤 상태가 되길 바라는가?

📝 나쁜 예 vs 좋은 예 비교

❌ 아이디어 중심 (나쁜 예)
"AI 기반 여행 플래너 앱"

"식당 추천 앱"

"펫시터 매칭 플랫폼"

✅ 문제 중심 (좋은 예)
"혼자 해외여행 가는 2030대가 동선 계획에 2시간 이상 쓴다"

"퇴근 후 혼자 저녁 장소를 10분 안에 결정하고 싶은 직장인"

"장기 출장 시 반려견 돌봄 믿을 수 있는 사람 찾기 어려운 1인 가구"

이유: 사용자·상황·불편·목표가 명확

💡 내 아이디어를 문제 정의로 바꾸는 방법

1
내 아이디어를 한 줄로 쓴다
예: "산책 대행 앱"
2
"이게 왜 필요한가?"를 3번 묻는다
왜? → "강아지 산책이 어려운 사람이 있어서" → 왜? → "혼자 사는 직장인은 퇴근이 늦어서" → 왜? → "강아지가 밖에 못 나가면 스트레스를 받아서"
3

결과: "야근이 잦은 1인 가구 직장인이 반려견 산책을 매일 챙기지 못해 죄책감을 느끼는 문제"

3. 핵심 사용자 흐름 설계하기

"핵심 흐름"이란 사용자가 서비스에 들어와서 가장 중요한 작업을 완료하기까지의 경로입니다.
이 흐름을 먼저 설계해야 어떤 화면과 기능이 필요한지 정확히 알 수 있습니다.

📐 공식: 입력 → 처리 → 결과
사용자가 무엇을 입력하면, 시스템이 어떻게 처리해서, 어떤 결과를 보여주는가?

📋 핵심 흐름 예시 — 반려동물 산책 매칭 서비스

📄 핵심 사용자 흐름 예시
입력: 보호자가 산책 희망 날짜, 시간, 위치, 반려견 정보를 입력
처리: 해당 조건에 맞는 산책 도우미 목록을 거리순으로 정렬 표시
결과: 보호자가 도우미를 선택하고 예약 완료 확인 메시지를 받음

핵심 흐름 화면: 홈 → 조건 입력 → 도우미 목록 → 상세보기 → 예약 완료
💡 주의: 핵심 흐름은 반드시 1개여야 합니다. Day 2에서 여러 흐름을 설계하려고 하면 범위가 너무 커집니다.
Must 기능은 이 하나의 핵심 흐름을 완성하는 데 필요한 것들만으로 제한합니다.

4. PROJECT.md 14섹션 완전 이해하기

PROJECT.md는 내 서비스의 모든 것을 담은 "설계 도면"입니다. 아래 14개 섹션 각각의 의미와 작성 방법을 이해하세요.

섹션 1
## Project Overview — 프로젝트 한 줄 요약
이 서비스가 무엇인지 한두 문장으로 설명. 처음 보는 사람도 이해해야 함.
예: "야근이 잦은 직장인이 신뢰할 수 있는 반려견 산책 도우미를 10분 안에 예약할 수 있는 매칭 서비스"
섹션 2
## Problem — 해결하려는 문제
앞서 정의한 4요소 문제 문장. 실제 사용자의 불편을 데이터나 상황으로 표현.
예: "야근 직장인의 73%가 반려견 산책을 주 3회 미만 시킨다(불편함 원인 상위 1위: 시간 부족)"
섹션 3
## Target User — 핵심 타겟 사용자
가장 이 서비스가 필요한 한 명의 구체적인 사람. 나이, 상황, 습관까지.
예: "25~35세, 서울 거주, 주 5일 이상 야근하는 1인 가구 직장인, 반려견 보유"
섹션 4
## Current Alternatives — 현재 대안과 한계
사용자가 지금 이 문제를 어떻게 해결하고 있는가? 왜 그 방법이 불충분한가?
예: "지인 부탁 → 부탁하기 눈치 보임. 일반 펫시터 앱 → 후기 신뢰성 불투명"
섹션 5
## Core Value and Hypothesis — 핵심 가치와 가설
내 서비스가 기존 대안보다 나은 점. 가설이므로 검증 필요.
예: "인증된 도우미 + 실시간 산책 경로 공유로 신뢰 문제 해결. 직장인 80%는 이를 위해 월 3만원 지불 의향"
섹션 6
## Core User Flow — 핵심 사용자 흐름
입력→처리→결과 형태의 한 줄 흐름. 화면 목록 포함.
예: "조건 입력 → 도우미 목록 → 상세 → 예약 완료"
섹션 7
## Features and Acceptance Criteria — 기능과 완료 기준
Must/Should/Could로 분류한 기능 목록. 각 기능마다 "이렇게 동작하면 완료"라는 기준 필요.
예: "Must: 도우미 목록 화면 → '목록에서 도우미를 클릭하면 상세 화면으로 이동'"

섹션 8
## Screen List — 화면 목록
서비스를 구성하는 화면들. MVP는 3~5개로 제한.
예: "홈, 조건 입력, 도우미 목록, 도우미 상세, 예약 완료"
섹션 9
## Data Model — 데이터 구조
서비스에서 다루는 데이터 종류. 어떤 정보를 저장하고 표시하는가.
예: "도우미: 이름, 사진, 위치, 가격, 평점 / 예약: 날짜, 시간, 보호자ID, 도우미ID"
섹션 10
## Technical Requirements — 기술 요건
어떤 기술 스택으로 만들지. 초보자는 "HTML/CSS/JS 단일 파일"로 설정.
예: "HTML/CSS/JavaScript, localStorage로 데이터 관리, 외부 API 미사용"
섹션 11
## MVP Scope — MVP 범위
이번 개발에서 반드시 완성해야 하는 것. Must 기능 3~5개로 제한.
예: "Must: 도우미 목록 표시, 도우미 상세보기, 예약 신청 폼"
섹션 12
## Out of Scope — 이번에 만들지 않는 것
나중에 만들 기능을 미리 선언. AI가 범위를 넘지 않도록 명시.
예: "회원가입/로그인, 결제 시스템, 실시간 채팅, 지도 API 연동"
섹션 13
## Risks and Open Questions — 위험과 미결 사항
아직 확인되지 않은 사항, 결정이 필요한 것들을 솔직하게 나열.
예: "Q: 도우미 데이터는 실제로 어떻게 입력할 것인가? (현재 임시 더미 데이터 사용 예정)"
섹션 14
## Demo Scenario — 데모 시나리오
발표 때 보여줄 5분 데모의 흐름. "나는 OOO로 시작해서 OOO를 보여줄 것"
예: "홈에서 날짜 선택 → 도우미 3명 목록 표시 → '박산책' 클릭 → 상세 확인 → 예약 신청 버튼 클릭 → 완료 메시지"

5. 완성된 PROJECT.md 예시 (전체)

아래는 "반려동물 산책 매칭" 서비스를 기준으로 작성한 PROJECT.md 전체 예시입니다. 여러분의 서비스에 맞게 수정하세요.

📄 PROJECT.md 완성 예시 (반려동물 산책 매칭)
# PROJECT.md — 반려동물 산책 매칭 서비스

## 1. Project Overview
야근이 잦은 1인 가구 직장인이 신뢰할 수 있는
반려견 산책 도우미를 10분 안에 예약하는 매칭 서비스

## 2. Problem
야근 직장인의 73%가 반려견 산책을 주 3회 미만 시킴
원인: 퇴근 후 너무 늦거나, 지인에게 부탁하기 눈치 보임

## 3. Target User
25~35세, 서울 거주, 주 5일 이상 야근, 1인 가구, 소형견 보유

## 4. Current Alternatives
- 지인 부탁: 관계 부담
- 기존 펫시터 앱: 후기 신뢰성 불투명, UI 복잡

## 5. Core Value
인증된 도우미 + 간단한 예약 3단계로 신뢰 문제 해결

## 6. Core User Flow
입력: 날짜, 시간, 위치, 견종
처리: 조건 맞는 도우미 목록 표시 (거리순)
결과: 도우미 선택 → 예약 완료 확인
화면: 홈 → 조건입력 → 도우미목록 → 상세보기 → 예약완료

## 7. Features (Must 3개만)
1. 도우미 목록 화면 — 카드 형태 3개 이상 표시
2. 도우미 상세 화면 — 이름, 소개, 가격, 후기
3. 예약 신청 폼 — 날짜/시간 입력 후 신청 버튼

## 12. Out of Scope
회원가입, 결제, 실시간 채팅, 지도 API

## 13. Open Questions
- 도우미 데이터: 임시 더미 데이터 3명 사용
- 예약 저장: localStorage 사용

## 14. Demo Scenario
홈 → 조건 입력 → 도우미 '박산책' 선택
→ 상세보기 확인 → 예약 신청 → 완료 메시지

📝 실습 1 — 한 장 서비스 정의서 만들기

내 아이디어를 AI와 함께 체계적인 문제 정의로 발전시킵니다.

📌 Codex 프롬프트: 내가 만들 서비스를 한 장 정의서로 작성해줘. 내 아이디어: [여기에 내 아이디어를 구체적으로 적어줘] 작성 항목: 1. 목표 사용자 — 나이, 상황, 생활 패턴까지 구체적으로 2. 사용자 문제 — 현재 상황, 불편한 점, 지금 어떻게 해결하는지 3. 핵심 가치 제안 — 내 서비스가 기존보다 나은 점 4. 한 줄 서비스 문장 — "OOO가 OOO 상황에서 OOO를 OOO할 수 있는 서비스" 주의: 임의로 사실을 추가하지 마. 불확실한 부분은 질문으로 남겨줘.

📝 실습 2 — 핵심 흐름·화면·데이터 구조화

📝 실습 3 — PROJECT.md 14섹션 작성

8. 흔히 하는 실수 Top 5

🚫 실수 1: Must에 너무 많이 넣기
"회원가입, 결제, 리뷰, 채팅, 지도..." → Must는 핵심 흐름에 필요한 3~5개만!

프롬프트에 "임의로 추가하지 마세요"를 꼭 넣고, AI 결과물을 반드시 검토하세요.

🚫 실수 4: 완료 기준 없이 기능만 나열
"예약 기능" → "사용자가 예약 버튼을 클릭하면 확인 메시지가 나타날 것"처럼 검증 가능하게.
🚫 실수 5: Out of Scope를 비워두기
AI는 비어있는 공간을 임의로 채웁니다. "만들지 않을 것"을 명확히 적어야 합니다.
