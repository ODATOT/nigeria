2. 최종 검증 3단계 피라미드

배포 전 서비스가 제대로 동작하는지 아래 3단계 순서로 확인합니다.

1
기능 검증 — Must 기능이 모두 동작하는가?
PROJECT.md ## 7. Features의 Must 기능을 하나씩 직접 클릭해서 확인.
VALIDATION.md에 통과/미통과를 기록합니다.
2
시나리오 검증 — 핵심 흐름이 끊기지 않는가?
PROJECT.md ## 14. Demo Scenario를 그대로 따라 해봅니다.
처음부터 끝까지 막힘 없이 동작하면 통과.
3
예외 검증 — 빈 값, 잘못된 입력에서 오류 메시지가 나오는가?
필수 입력란을 비우고 제출, 이상한 값을 입력해도 서비스가 멈추지 않는지 확인.

📋 최종 검증 Codex 프롬프트

📌 Codex 요청: VALIDATION.md를 최종 업데이트해줘. 검증 기준: PROJECT.md ## 7. Features의 Must 기능 전체 표 형식으로 작성: | 기능명 | 검증 방법 | 결과(통과/미통과) | 비고 | 추가로 아래 공통 예외 사항도 검증 항목에 추가해줘: - 필수 입력 빈 칸 제출 시 오류 메시지 표시 여부 - 목록 Empty State 메시지 표시 여부 - 브라우저 새로고침 후 데이터 유지 여부 (localStorage)

3. GitHub Pages로 온라인 배포하기

🌐 배포란? 내 컴퓨터에서만 보이던 서비스를 인터넷에 올려 누구나 URL로 접속할 수 있게 하는 것입니다.
GitHub Pages는 무료로 HTML 파일을 온라인에 배포할 수 있는 서비스입니다.

📌 GitHub Pages 배포 단계별 가이드

1
GitHub 계정 만들기 (없다면)
github.com 접속 → Sign Up → 이메일 인증 완료
2
새 Repository(저장소) 만들기
우측 상단 + 버튼 → New repository
이름: my-project (또는 서비스 이름)
Public 선택 → Create repository 클릭
3
파일 업로드
"uploading an existing file" 클릭 → my-project 폴더의 index.html을 드래그앤드롭
Commit message: "Day 5: Final MVP upload" → Commit changes 클릭
4
GitHub Pages 설정
Repository → Settings → Pages (좌측 메뉴)
Source: "Deploy from a branch" → Branch: main → / (root) → Save
5
배포 URL 확인
1~3분 후 Pages 설정 화면 상단에 URL이 나타납니다:
형식: https://[GitHub 아이디].github.io/my-project
이 URL을 팀원, 멘토에게 공유하세요!
💡 배포 후 수정하려면?
index.html 수정 → GitHub Repository 접속 → index.html 파일 클릭 → ✏️ 편집 버튼 → 수정 후 Commit
자동으로 사이트가 업데이트됩니다 (1~2분 소요).

4. 5분 발표 이야기 구조 만들기

훌륭한 5분 발표는 기술 설명이 아니라 이야기입니다. 아래 구조를 따르면 청중이 집중합니다.

파트시간내용
① 훅 (Hook) 30초 청중이 공감할 수 있는 문제 상황 한 문장
② 문제 45초 누가, 어떤 상황에서, 왜 불편한가?
③ 해결책 30초 내 서비스가 어떻게 이 문제를 해결하는가?
④ 라이브 데모 2분 실제 서비스 화면으로 핵심 흐름 시연
⑤ 성과와 배운 점 45초 5일 동안 만들면서 배운 것, 다음에 추가할 기능
⑥ 마무리 30초 한 줄 요약 + 배포 URL 공유

📝 발표 스크립트 작성 예시 (반려동물 산책 매칭)

① 훅 (30초)
"야근 후 집에 돌아왔을 때 강아지가 하루 종일 못 나간 걸 알면서도 너무 지쳐서 산책을 못 시킨 경험이 있으신가요?
저는 그 죄책감이 너무 싫어서 이 서비스를 만들었습니다."
② 문제 (45초)
"1인 가구 야근 직장인의 73%가 반려견을 주 3회 미만 산책시킨다는 통계가 있습니다.
지인에게 부탁하기엔 눈치 보이고, 기존 앱은 후기를 믿기 어렵습니다.
결국 반려견도, 보호자도 스트레스를 받게 됩니다."
③ 해결책 (30초)
"저는 3단계로 간단히 신뢰할 수 있는 산책 도우미를 예약하는 서비스를 만들었습니다.
조건 입력 → 도우미 목록 → 예약 완료. 5분도 안 걸립니다."
④ 라이브 데모 (2분)
"지금 바로 보여드리겠습니다. 이 URL로 접속하면 됩니다.
[화면 공유] 날짜를 선택하고... 박산책 도우미를 선택하면... 예약 완료!
[즐겨찾기] 이처럼 마음에 드는 도우미를 저장할 수도 있습니다."
⑤ 성과와 배운 점 (45초)
"5일 만에 처음으로 혼자 동작하는 웹 서비스를 만들었습니다.
AI 도구에게 막연하게 요청하면 원하는 결과가 안 나온다는 것을 배웠습니다.
다음에는 실제 결제 기능과 실시간 위치 공유를 추가하고 싶습니다."
⑥ 마무리 (30초)
"'야근 직장인의 반려견 산책 걱정을 해결하는 10분 예약 서비스'입니다.
지금 바로 이 URL에서 사용해볼 수 있습니다: https://username.github.io/my-project
감사합니다!"

📌 Codex로 발표 스크립트 생성하기

📌 Codex 요청: PROJECT.md를 기반으로 5분 발표 스크립트를 작성해줘. 구조: 1. 훅 (30초): 청중이 공감할 문제 상황 한 문장 2. 문제 설명 (45초): Target User의 불편과 현재 대안의 한계 3. 해결책 소개 (30초): 핵심 가치 제안 4. 데모 시나리오 (2분): ## 14. Demo Scenario 기반 단계별 설명 5. 성과 (45초): 만들면서 배운 점, 다음에 추가할 기능 6. 마무리 (30초): 한 줄 요약 + URL 파일명: PRESENTATION_SCRIPT.md로 저장해줘.

5. 발표 후 예상 Q&A 10가지

Q1. 왜 이 문제를 선택했나요?
A: 직접 경험하거나 주변에서 자주 보이는 문제를 선택했습니다. [구체적 경험 언급]
Q2. 기존 앱과 무엇이 다른가요?
A: PROJECT.md ## 4. Current Alternatives에 정리한 기존 대안의 한계와 내 서비스의 차이를 설명합니다.
Q3. 실제로 사용자가 있나요?
A: 아직 MVP 단계입니다. 다음 단계는 지인 5명에게 직접 써보게 하고 피드백을 받을 계획입니다.
Q4. 어떻게 돈을 버나요?
A: 현재는 서비스 가능성 검증이 목표입니다. 향후 수수료 모델을 검토 중입니다.
Q5. 데이터는 어디에 저장되나요?
A: MVP는 브라우저 localStorage에 저장됩니다. 실제 서비스에서는 서버 DB로 전환할 계획입니다.
Q6. 5일 만에 혼자 만들었나요?
A: Codex와 Antigravity(AI 개발 도구)를 활용했습니다. AI가 코드를 생성하고, 저는 요구사항 문서와 방향을 결정했습니다.
Q7. 가장 어려웠던 부분은?
A: AI에게 명확하게 요청하는 방법을 배우는 것이 가장 어려웠습니다. 구체적인 완료 기준을 쓰는 것이 핵심이었습니다.
Q8. 다음에 뭘 추가할 건가요?
A: NEXT_STEPS.md에 정리한 내용입니다. [우선순위 1~3위 기능 언급]
Q9. 모바일에서도 되나요?
A: 네, 반응형으로 설계해서 스마트폰에서도 사용 가능합니다. 직접 QR코드로 확인해보세요.
Q10. 이 서비스를 실제로 창업할 생각인가요?
A: 이번 5일 과정을 통해 아이디어를 실제로 만드는 방법을 배웠습니다. 사용자 반응을 더 보고 결정하겠습니다.
