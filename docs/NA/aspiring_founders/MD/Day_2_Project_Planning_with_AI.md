### 5.1 아이디어와 문제의 차이 — 10분

#### 전달할 내용

- 아이디어는 만들고 싶은 해결책이고, 문제는 사용자가 현재 겪는 불편이다.
- 기술이나 기능부터 정하면 실제 사용자 문제와 관계없는 제품이 되기 쉽다.
- “AI”, “플랫폼”, “자동화” 같은 단어는 문제 자체가 아니다.
- 문제 문장에는 최소한 **사용자, 상황, 어려움, 원하는 변화**가 들어가야 한다.

#### 비교 예시

```text
[아이디어 중심]
AI를 활용한 여행 서비스를 만든다.

[문제 중심]
처음 방문하는 도시에서 짧은 시간 안에 일정을 정해야 하는 1인 여행자가
여러 사이트를 반복해서 검색하느라 이동 가능한 하루 일정을 만들기 어렵다.

[원하는 변화]
사용자가 선호 장소와 체류 시간을 입력하면 이동 가능한 하루 일정을
10분 이내에 확인할 수 있게 한다.
```

#### 강사 질문

- 이 문장에서 실제 사용자는 누구인가?
- 사용자가 서비스를 찾게 되는 구체적인 순간은 언제인가?
- 사용자가 현재 사용하는 방법은 무엇인가?
- 불편이 사라졌다는 것을 어떤 결과로 확인할 수 있는가?

#### 사용할 이미지

- **파일명:** `01_idea_vs_problem.png`
- **예정 경로:** `../LECTURE/assets/day2/01_idea_vs_problem.png`

- **강조 문구:** `아이디어 = 만들고 싶은 것 / 문제 = 사용자가 현재 겪는 것`

### 5.2 문제와 목표 사용자 구체화 — 20분

#### 전달할 내용

“모든 사람”은 목표 사용자가 아니다. 동일한 사람도 상황에 따라 다른
문제를 느낀다. 인구통계만 나열하기보다 행동과 문제 발생 상황을 중심으로
사용자를 정의한다.

다음 다섯 항목을 순서대로 구체화한다.

1. **사용자:** 이 문제를 가장 자주 또는 강하게 겪는 사람
2. **상황:** 문제가 발생하는 시간, 장소, 계기
3. **현재 행동:** 지금 문제를 해결하기 위해 하는 일
4. **불편과 비용:** 시간, 돈, 반복 작업, 불안, 실수
5. **원하는 변화:** 서비스 사용 후 달라져야 하는 상태

#### 사용자 정의 템플릿

```text
[사용자]는 [상황]에서 [목표]를 달성하려고 하지만,
현재 [대안/행동] 때문에 [구체적인 불편/비용]을 겪는다.
```

#### 예시

```text
여행 계획 경험이 적은 1인 여행자는 출발 전날 제한된 시간 안에
하루 일정을 만들려고 하지만, 지도와 블로그를 반복해서 확인하기 때문에
장소 간 이동 시간을 반영한 일정을 완성하기 어렵다.
```

#### 3분 판단 활동

강사가 다음 두 사용자 정의를 보여주고 더 개발 가능한 문장을 고르게 한다.

```text
A. 여행을 좋아하는 20~40대
B. 출발 전날 30분 안에 하루 동선을 정해야 하는 여행 계획 초보자
```

정답을 고르는 것보다 B가 **상황과 행동을 관찰할 수 있어 검증하기 쉽다**는
점을 설명한다.

### 5.3 핵심 가치와 사용자 흐름 — 15분

#### 전달할 내용

- **핵심 가치:** 사용자가 기존 방법보다 빠르고 쉽게 얻는 변화
- **핵심 행동:** MVP에서 사용자가 처음부터 끝까지 수행해야 하는 한 가지 행동
- **성공 결과:** 핵심 행동이 실제로 완료됐음을 화면이나 데이터로 확인하는 조건
- 기능 목록보다 입력에서 결과까지 이어지는 한 개의 흐름을 먼저 정한다.

#### 사용자 흐름 예시

```text
입력: 선호 장소와 여행 가능 시간 입력
처리: 조건에 맞는 방문 순서와 이동 동선 생성
결과: 사용자가 일정표를 확인하고 저장
```

```text
홈 → 조건 입력 → 일정 생성 → 결과 확인 → 일정 저장
```

### 5.4 기능 요구사항과 완료 조건 — 15분

#### 전달할 내용

“일정 추천 기능을 만든다”는 개발 완료 여부를 판단하기 어렵다. 기능을
사용자 목적, 입력, 처리, 출력, 예외 상황과 완료 조건으로 나누면
Antigravity가 구현하고 Codex가 검증할 수 있는 명세가 된다.

```text
기능 이름:
사용자 목적:
입력:
처리:
출력:
예외 상황:
완료 조건:
```

#### 작성 예시

```text
기능 이름: 하루 일정 생성
사용자 목적: 제한된 시간에 방문 가능한 장소 순서를 확인한다.
입력: 선호 장소 1개 이상, 시작 시간, 종료 시간
처리: 입력 시간을 벗어나지 않도록 장소 방문 순서를 구성한다.
출력: 방문 순서, 예상 시간, 장소별 체류 시간
예외 상황: 장소 미선택, 시작 시간이 종료 시간보다 늦음
완료 조건:
- 올바른 입력 시 결과 화면에 방문 순서가 표시된다.
- 장소를 선택하지 않으면 입력 화면에 안내 문구가 표시된다.
- 시작 시간이 종료 시간보다 늦으면 생성 버튼이 실행되지 않는다.
```

- 어떤 입력값이 반드시 필요한가?
- 사용자가 잘못 입력하면 어떤 화면을 보게 되는가?
- “잘 동작한다”를 눈으로 확인할 수 있는 문장으로 바꾸면 무엇인가?

### 5.5 MVP 범위 결정 — 10분

#### 전달할 내용

- **Must:** 핵심 사용자 흐름에 반드시 필요
- **Should:** 시간이 허용되면 추가
- **Could:** 데모 이후 개선
- **Out of Scope:** 이번 교육에서 구현하지 않음

회원가입·결제·관리자 기능은 핵심 가설 검증에 꼭 필요한 경우에만 Must에
포함한다. 기능을 제거하는 것이 아니라 구현 시점을 뒤로 옮기는 결정임을
강조한다.

#### 기능 분류 예시

| 기능 | 분류 | 이유 |
|---|---|---|
| 여행 조건 입력 | Must | 핵심 결과를 만들기 위한 입력 |
| 일정 결과 확인 | Must | 핵심 가치가 전달되는 결과 |
| 일정 저장 | Must 또는 Should | 데모 가설에 따라 결정 |
| 소셜 로그인 | Could | 핵심 일정 생성은 로그인 없이 검증 가능 |
| 실제 결제 | Out of Scope | 핵심 가설과 무관하고 교육 범위를 초과 |

#### 사용할 이미지

- **파일명:** `06_mvp_priority_funnel.png`
- **예정 경로:** `../LECTURE/assets/day2/06_mvp_priority_funnel.png`
- **화면 비율:** 16:9
- **구성:** 많은 기능 카드가 깔때기를 통과해 3~5개의 Must 카드만 남는 모습. 아래에 Should, Could, Out of Scope 보관함을 표시한다.
- **강조 문구:** `MVP는 작은 기능 목록이 아니라 완성된 핵심 흐름`
- **대체 텍스트:** 기능 후보를 우선순위에 따라 줄여 Must 기능을 선택하는 깔때기
- **사용 시점:** 실제 결제와 소셜 로그인을 Must에서 제외하는 판단을 설명할 때 사용한다.

### 실습 4. 기능 우선순위 결정과 MVP 범위 줄이기

`PROJECT.md`에 작성한 모든 기능을 다음 네 단계로 분류한다.

| 우선순위 | 판단 기준 | 처리 방법 |
|---|---|---|
| Must | 핵심 사용자 흐름이 동작하는 데 반드시 필요 | 이번 MVP에서 구현 |
| Should | 사용자 경험에 중요하지만 없어도 핵심 흐름은 동작 | Must 완료 후 구현 |
| Could | 있으면 좋지만 핵심 가설 검증과 직접 관련 없음 | 향후 개선 목록으로 이동 |
| Out of Scope | 5일 안에 구현하거나 검증하기 어려움 | 이번 과정에서 제외 |

#### 진행 방법

1. 기능별로 “이 기능이 없어도 핵심 사용자 행동을 완료할 수 있는가?”를 묻는다.
2. 답이 “예”라면 우선 Must에서 제외한다.
3. Must 기능을 최대 3~5개로 제한한다.
4. 제거한 기능은 삭제하지 않고 `Should`, `Could`, `Out of Scope`로 이동한다.
5. Codex에 현재 범위가 2일 동안 구현 가능한지 비판적으로 검토하도록 요청한다.

#### Codex 활용 프롬프트 예시

```text
PROJECT.md의 MVP 범위를 검토해 주세요.
핵심 사용자 흐름을 완성하는 데 꼭 필요하지 않은 기능을 찾아주세요.
각 기능을 Must, Should, Could, Out of Scope로 분류하고 근거를 설명해 주세요.
Must는 3~5개로 제한하고, 최종 결정 전에는 문서를 직접 수정하지 마세요.
```

**완료 기준**

- Must 기능이 3~5개 이내다.
- 모든 Must 기능이 핵심 사용자 흐름과 직접 연결된다.
- 이번 과정에서 구현하지 않을 범위가 명확히 기록되어 있다.
- 우선순위 결정 이유를 수강생이 직접 설명할 수 있다.

5. Codex에 지시문의 모호함과 누락을 검토하도록 요청한다.

**완료 기준**

- 지시문이 `PROJECT.md`를 단일 기준 문서로 참조한다.
- 첫 번째 구현 범위가 한 번에 테스트 가능한 크기다.
- Must와 제외 범위가 명시되어 있다.
- 실행 및 확인 가능한 완료 기준이 포함되어 있다.
- Day 3에 그대로 사용할 수 있는 최종 프롬프트가 저장되어 있다.

## 7. 학생용 따라하기 실습 워크북

### 7.0 공통 진행 방식

모든 실습은 강사가 예시 화면으로 한 구간을 먼저 보여주고 학생이 같은
구간을 자신의 아이디어로 따라 하는 방식으로 진행한다.

```text
강사 시연 3~5분 → 학생 따라 하기 5~10분 → 짝과 확인 2분
→ 완료 화면 체크 → 다음 구간 이동
```

학생은 각 구간을 끝낼 때 결과 파일을 저장하고 체크박스를 표시한다.
강사는 전체 학생의 80% 이상이 필수 확인 항목을 완료한 뒤 다음 구간으로
이동한다. 빨리 끝낸 학생은 선택 도전 항목을 수행한다.

#### 공통 화면 배치

학생이 강의 화면과 자신의 작업 화면을 동시에 볼 수 있도록 다음 배치를
권장한다.

```text
┌──────────────────────── 강사 프로젝터 ────────────────────────┐
│ ① 현재 구간  │ ② 입력 예시/프롬프트 │ ③ 완료 화면 │ 체크 항목 │
└───────────────────────────────────────────────────────────────┘

┌────────────── 학생 화면 왼쪽 ──────────────┬──── 학생 화면 오른쪽 ────┐
│ Codex 대화 또는 PROJECT.md                  │ 따라하기 가이드/체크리스트 │
└─────────────────────────────────────────────┴──────────────────────────┘
```

#### 학생용 파일 구성

```text
my-startup-mvp/
├── IDEA_NOTES.md          # 실습 1 입력 메모
├── SERVICE_STRUCTURE.md   # 실습 2 화면·흐름·데이터
├── PROJECT.md             # 실습 3~5 통합 기획 문서
├── HANDOFF_PROMPT.md      # 실습 6 Antigravity 전달 지시문
└── REVIEW_NOTES.md        # 동료 피드백과 수정 기록
```

### 7.1 실습 1 따라하기 — 한 장 서비스 정의

#### 시작 화면

학생은 Codex에서 자신의 프로젝트 폴더를 연 뒤 빈 `IDEA_NOTES.md`를
준비한다. 강사는 완성본을 먼저 보여주지 않고 아래 다섯 질문만 화면에
표시한다.

```text
1. 누가 이 문제를 겪는가?
2. 언제 이 문제가 발생하는가?
3. 지금은 어떻게 해결하는가?
4. 무엇이 불편하거나 비효율적인가?
5. 서비스 사용 후 무엇이 달라져야 하는가?
```

#### 구간별 진행

| 구간 | 시간 | 학생이 할 일 | 강사 시연 | 확인 결과 |
|---|---:|---|---|---|
| 1-A | 8분 | 다섯 질문에 각각 1~2문장으로 답한다. | 여행 서비스의 짧은 메모 작성 | `IDEA_NOTES.md`에 원문 메모가 있다. |
| 1-B | 10분 | Codex로 사용자 문제 문장 세 가지를 만든다. | 모호한 표현을 상황·행동으로 바꾸기 | 문제 문장 후보 3개가 있다. |
| 1-C | 10분 | 가장 구체적인 문장을 선택하고 직접 수정한다. | AI 문장에서 임의 추측 찾기 | 최종 문제 문장 1개가 있다. |
| 1-D | 8분 | 핵심 가치와 성공 행동을 한 문장으로 작성한다. | 결과를 측정 가능한 행동으로 바꾸기 | 핵심 가치·성공 행동이 있다. |
| 1-E | 4분 | 짝에게 읽어주고 이해되지 않는 단어를 표시한다. | 30초 설명 예시 | 동료 질문 1개가 기록된다. |

#### 학생 입력 예시

```text
서비스 아이디어: AI 여행 일정 만들기
사용자: 여행 계획을 처음 세우는 1인 여행자
상황: 출발 전날 30분 안에 하루 동선을 정해야 한다.
현재 대안: 지도, 블로그, 메모장을 번갈아 사용한다.
불편: 장소 간 이동 시간을 직접 계산하기 어렵다.
원하는 변화: 조건을 입력하고 이동 가능한 일정표를 확인한다.
```

#### 따라 하기 프롬프트

```text
IDEA_NOTES.md를 읽고 사용자 문제 문장 후보를 세 개 작성해 주세요.
각 문장은 사용자, 문제 발생 상황, 현재 행동, 구체적인 불편을 포함해야 합니다.
제가 제공하지 않은 사실은 추가하지 말고, 부족한 정보는 질문으로 분리해 주세요.
파일은 아직 수정하지 마세요.
```

#### 실습 포인트

- Codex의 첫 결과를 그대로 복사하지 않고 원문에 없는 추측을 표시한다.
- “누구나”, “편리하게”, “효율적으로”처럼 확인하기 어려운 단어를 구체화한다.
- 기능이나 기술보다 문제와 사용 상황을 먼저 작성한다.

#### 예시 완료 화면

```text
┌─ IDEA_NOTES.md ───────────────────────────────────────────────┐
│ Problem                                                       │
│ 출발 전날 30분 안에 하루 동선을 정해야 하는 여행 계획 초보자가 │
│ 지도와 블로그를 반복 확인하며 이동 가능한 일정을 만들기 어렵다. │
│                                                               │
│ Core Value                                                    │
│ 선호 장소와 시간을 입력해 이동 가능한 하루 일정을 확인한다.    │
│                                                               │
│ Success Action                                                │
│ 생성된 일정표를 확인하고 저장한다.                             │
└───────────────────────────────────────────────────────────────┘
```

**완료 체크**

- [ ] 사용자, 상황, 현재 대안과 불편이 한 문장에 드러난다.
- [ ] 핵심 가치가 기능 이름이 아닌 사용자 변화로 작성됐다.
- [ ] AI가 임의로 추가한 내용을 제거하거나 질문으로 분리했다.

### 7.2 실습 2 따라하기 — 핵심 흐름·화면·데이터 만들기

#### 시작 화면

강사는 실습 1의 성공 행동을 화면 가운데 놓고, 그 행동에 도달하기 위해
필요한 앞 단계만 역순으로 질문한다.

#### 구간별 진행

| 구간 | 시간 | 학생이 할 일 | 강사 시연 | 확인 결과 |
|---|---:|---|---|---|
| 2-A | 8분 | 성공 행동까지의 단계를 5개 이내로 작성한다. | 저장←결과 확인←일정 생성 역순 작성 | 핵심 흐름 한 줄이 있다. |
| 2-B | 10분 | 각 단계를 화면 이름으로 바꾼다. | 행동과 화면 구분하기 | 화면 목록이 있다. |
| 2-C | 10분 | 화면별 입력·행동·결과를 표로 작성한다. | 조건 입력 화면 한 행 작성 | 화면 명세 표가 있다. |
| 2-D | 8분 | 화면에서 필요한 데이터만 추출한다. | 장소·시간 데이터 구분 | 데이터 목록이 있다. |
| 2-E | 4분 | 흐름이 끊기는 단계에 물음표를 표시한다. | 미결정 사항 기록 | 질문 목록이 있다. |

#### 예시 핵심 흐름

```text
홈 → 여행 조건 입력 → 일정 생성 → 결과 확인 → 일정 저장
```

#### 예시 화면 와이어프레임

```text
┌──────────── 여행 조건 입력 ────────────┐
│ 여행 도시        [ 서울            ]  │
│ 선호 장소        [ + 장소 선택      ]  │
│ 시작 시간        [ 10:00 ▼         ]  │
│ 종료 시간        [ 18:00 ▼         ]  │
│                                         │
│              [ 일정 만들기 ]           │
│ * 장소를 1개 이상 선택해 주세요.       │
└─────────────────────────────────────────┘
```

```text
┌──────────── 생성된 하루 일정 ──────────┐
│ 10:00  경복궁        예상 체류 90분    │
│   ↓     이동 25분                       │
│ 12:00  광장시장      예상 체류 60분    │
│   ↓     이동 20분                       │
│ 14:00  동대문        예상 체류 90분    │
│                                         │
│ [다시 만들기]               [저장하기] │
└─────────────────────────────────────────┘
```

#### 실습 포인트

- 화면 수를 늘리기보다 핵심 흐름의 시작과 끝을 연결한다.
- 모든 Must 기능은 화면 한 곳 이상에서 확인할 수 있어야 한다.
- 데이터는 “사용자 데이터”처럼 크게 쓰지 않고 필드 단위로 작성한다.
- 빈 값과 오류 안내가 어느 화면에 나타나는지 표시한다.

**완료 체크**

- [ ] 핵심 사용자 흐름이 5단계 이내다.
- [ ] 각 단계가 구체적인 화면과 연결된다.
- [ ] 화면별 사용자 행동과 시스템 결과가 구분돼 있다.
- [ ] 입력·결과 화면에 필요한 데이터가 정의돼 있다.

#### 따라 하기 프롬프트

```text
IDEA_NOTES.md와 SERVICE_STRUCTURE.md를 읽어 주세요.
아직 파일을 만들거나 수정하지 말고 다음만 표로 정리해 주세요.
1. 두 문서에서 확정된 내용
2. 서로 모순되는 내용

```

질문에 답한 후 문서 생성을 요청한다.

```text
지금까지 확정한 내용만 사용해 PROJECT.md를 작성해 주세요.
문서 구조는 Day 2 커리큘럼의 14개 섹션을 따릅니다.
확정되지 않은 내용은 Risks and Open Questions에 남겨 주세요.
Must 기능별로 화면에서 확인할 수 있는 Acceptance Criteria를 작성해 주세요.

```

#### 예시 완료 화면

```text
┌─ PROJECT.md 문서 탐색 ───────┬─ 현재 섹션 ────────────────────┐
│ 1. Project Overview          │ 7. Features and Acceptance     │
│ 2. Problem                   │                                │
│ 3. Target User               │ Must 1. 여행 조건 입력         │
│ 4. Current Alternatives      │ - 장소 1개 이상 선택           │
│ 5. Core Value                │ - 시작/종료 시간 입력           │
│ 6. Core User Flow            │ - 빈 값 안내 표시               │
│ 7. Features...          ←    │                                │
│ ...                          │ Acceptance Criteria            │
│ 14. Demo Scenario            │ [ ] 정상 입력 시 결과 이동     │
└──────────────────────────────┴────────────────────────────────┘
```

#### 실습 포인트

- Codex가 문서를 만들기 전에 먼저 읽고 질문하도록 한다.
- 생성된 문서가 길다는 이유로 완성됐다고 판단하지 않는다.
- 원본 메모와 다른 내용은 반드시 승인 여부를 결정한다.
- 완료 조건은 “잘 보인다”가 아니라 입력과 기대 결과로 작성한다.

**완료 체크**

- [ ] `PROJECT.md`의 필수 섹션이 모두 있다.
- [ ] 미결정 사항이 확정 요구사항과 분리돼 있다.
- [ ] Must 기능별 완료 조건이 테스트 가능하다.
- [ ] Codex가 추가한 추측을 검토했다.

### 7.4 실습 4 따라하기 — MVP 범위 줄이기

#### 구간별 진행

| 구간 | 시간 | 학생이 할 일 | 확인 결과 |
|---|---:|---|---|
| 4-A | 5분 | 모든 기능을 포스트잇처럼 한 줄씩 나열한다. | 전체 기능 목록 |
| 4-B | 8분 | 핵심 흐름에 없으면 Must에서 제거한다. | Must 1차 목록 |
| 4-C | 7분 | Codex에 2일 구현 위험을 비판적으로 검토하게 한다. | 위험 기능 표시 |

#### 예시 분류 보드

```text
┌──────── MUST ────────┬────── SHOULD ──────┬────── COULD ───────┐
│ 여행 조건 입력       │ 일정 저장           │ 소셜 로그인         │

│ 결과 확인            │                      │ 다국어                │
├──────────────────────┴─────────────────────┴────────────────────┤
│ OUT OF SCOPE: 실제 예약, 실결제, 실시간 교통 최적화             │
└─────────────────────────────────────────────────────────────────┘
```

#### 실습 포인트

- 기능을 삭제하지 않고 이후 목록으로 이동하면 범위를 줄이기 쉬워진다.
- 기술적으로 멋진 기능보다 핵심 가설에 필요한 기능을 남긴다.
- Codex의 분류는 제안일 뿐이며 최종 결정과 문서 수정은 학생이 승인한다.

**완료 체크**

- [ ] Must 기능이 3~5개 이내다.
- [ ] Out of Scope가 세 가지 이상 명시돼 있다.
- [ ] Must만으로 정상 시나리오를 완주할 수 있다.

| 5-E | 4분 | 누락 조건을 `PROJECT.md`에 반영한다. | 문서 갱신 |

#### 예시 시나리오 화면

```text
정상: 조건 입력 ──[생성]──▶ 일정 결과 ──[저장]──▶ 저장 완료

빈 값: 장소 미선택 ──[생성]──▶ “장소를 1개 이상 선택하세요”

실패: 조건 입력 ──[생성 실패]──▶ 오류 안내 + [다시 시도]
```

#### 실습 포인트

- 정상 화면만 정의하면 Antigravity가 오류 상태를 임의로 결정하게 된다.
- 오류 메시지는 원인과 다음 행동을 함께 알려야 한다.
- 시나리오의 모든 단계가 `PROJECT.md`의 완료 조건에 나타나야 한다.
